### 0.2 三条硬判断（先说不好听的）

1. **我们最大的技术风险不是"算法不够新"，是"AI 那一段跑不通"。** 需求基线里最怕的「AI 深度不足」——真正会让评审皱眉的不是没用 Transformer 新架构，而是**学生发一条"三食堂二楼排长队"，系统能不能稳定地把它变成 `{地点:三食堂, 楼层:2F, 类型:排队, 时间:12:10}`**。这件事 90% 靠工程判据，10% 靠模型。所以 P0 全是这一层。

2. **生成式推荐、原生 3D 生成大模型、世界模型这三条线，现阶段对我们都是"叙事资产"而非"工程资产"。** 可以在方案书里作为「技术演进方向 / 已完成可行性验证」写，但**不能排进 40 天的关键路径**。原因很硬：OneRec 是 4 亿 DAU 场景的端到端架构，我们连 1 万条交互都未必凑得齐；3D 生成基础模型的训练数据是几十万量级精选资产，我们连标注人力都没有。

3. **2026 年是 3D 格式的换代窗口，这件事的性价比高得离谱。** glTF 2.1（2026-06 发布计划）、`KHR_gaussian_splatting`（2026-02 进入候选发布）、3D Tiles 2.0（2026-06~07 公开征求意见）、SPZ 4（2026-05）—— 全挤在这一年。**我们现在导出的 GLB 只要保证「标准 glTF 2.0 + Draco/Meshopt + KTX2」这三件事做对，未来换任何渲染后端都不用返工。** 这条几乎零成本，但很多队伍会踩坑。

## 1. P0 · 直接决定核心闭环能不能跑通

### 1.1 约束解码 + 结构化事件抽取

| 项 | 内容 |
| --- | --- |
| **代表实现** | XGrammar（MLC/CMU，2024-11 论文）、Outlines（dottxt）、各大模型厂商原生 Structured Outputs（OpenAI 2024-08 起，国内厂商 2025 年陆续跟进） |
| **适用场景** | 把非结构化 UGC 文本 → 固定 Schema 的结构化事件对象 |
| **核心优势** | 从"提示词祈祷模型输出合法 JSON"升级为**token 级语法约束**：输出必然满足 JSON Schema / 正则 / CFG，**从根本上消除解析失败与字段幻觉**。2026 年的生产共识是：**所有工具调用参数与结构化抽取都应走约束解码**，而不是靠 prompt 里写"请只输出 JSON"。 |
| **可借鉴的具体点** | ① 定义一份**校园事件 Schema**（`事件类型 / 地点锚点 ID / 楼层 / 起止时间 / 严重度 / 证据类型 / 原文引用`），把它作为约束解码的 target；② 关键：**让模型同时输出"原文引用片段"字段**——这是后面可信度评分的证据链，事后补不出来；③ 地点字段不要让它自由生成，**约束为枚举我们已预埋的 `ANCHOR_*` 列表**（见 1.5）；④ 严重度分级直接进 Schema，别用自由文本。 |
| **坑** | 约束解码会**降低语义多样性**——如果 Schema 太细（比如 20 个字段），小模型会为了满足约束而乱填。**先粗后细**：第一版 Schema 控制在 6~8 个字段，跑通再扩。 |
| **证据强度** | ★★★ 论文 + 主流厂商生产实践 |

### 1.2 时空聚类去重（空间 + 时间 + 语义三路融合）

| 项 | 内容 |
| --- | --- |
| **代表实现** | HDBSCAN（密度聚类，可处理变密度与噪声，无需预设簇数）＋ 时空滑动窗口 ＋ 句向量相似度；学术界对应方向为 spatio-temporal social event detection（如 Deep-Eware 系的混合学习模型，2022 起） |
| **适用场景** | 50 个人同时上报"三食堂排队" → 聚成 **1 个事件**，而不是 50 个点糊在地图上 |
| **核心优势** | **不用训练**、参数可解释、能自动把噪声单帖标为离群点（正好对应"孤立上报可信度低"）。三路取交集比任何单路都稳：纯语义会把"三食堂排队"和"图书馆排队"混为一谈，纯空间会把"三食堂排队"和"三食堂停电"混为一谈。 |
| **可借鉴的具体点** | ① **判据写死**：同一事件 = `空间距离 < 150 m` **且** `时间差 < 45 min` **且** `句向量余弦 > 0.78`（数值需按我们自己的数据标定，先用这组跑基线）；② **HDBSCAN 的 `noise` 标签就是可信度先验**：被归为噪声的孤立上报，初始可信度直接打折；③ **簇的"人数"是最强信号**：5 人独立上报同一事件 ≫ 1 人上报 5 次（要按 `user_id` 去重后再数）；④ 事件合并后**保留全部原文与上报人列表**，前端做"12 人上报"的展开，这是社区感的关键。 |
| **坑** | ★★ **时空聚类本身不新，新的是"把它接在 LLM 抽取之后"**。如果抽取环节的地点字段是自由文本（"三食堂二楼靠窗" vs "第三食堂 2F"），空间距离根本算不出来。**1.1 和 1.2 必须一起做，顺序不能反。** |
| **证据强度** | ★★ 方法成熟，公开可复现；参数需自标定 |

### 1.3 检索增强的事实核查（Claim Verification）

| 项 | 内容 |
| --- | --- |
| **代表实现** | 《Claim Verification in the Age of Large Language Models: A Survey》（arXiv 2408.14317，收录于 **ACL 2026 SRW**）——系统梳理了 LLM 时代的事实核查框架：claim 拆解 → 证据检索 → 证据与 claim 的一致性判定 → 裁决与解释 |
| **适用场景** | ① 给每条事件/帖子打**可信度分**；② 安全类预警发布前的**交叉验证闸门**（需求基线明确点出的法律风险） |
| **核心优势** | 提供了**可直接抄的裁决结构**：不是让大模型"感觉一下真假"（不可审计、不可复现），而是「**拆 claim → 找证据 → 判 entail/contradict/neutral → 给理由**」。每一步都可留痕，正好满足竞赛材料对"算法说明"的要求。 |
| **可借鉴的具体点** | ① **三路证据源**：UGC 交叉（同事件独立上报人数）+ 官方源 RAG（保卫处/后勤通知）+ 常识一致性（"教学楼 3 号楼"是否存在——用 `ANCHOR_*` 列表校验）；② 裁决输出**三分类而非分数**：`支持 / 矛盾 / 无证据`，再映射成分数（如 1.0 / 0.0 / 0.5）——比让模型直接吐 0~1 更稳；③ **安全类事件走强制闸门**：可信度 < 阈值时**不自动打点**，进人工审核队列，前端只显示"待核实"灰色标记。这条要写进方案书，是加分项；④ **解释生成**：把证据片段作为推荐理由返回给用户（"3 位同学在 10 分钟内报告同一情况"）——可解释性直接变产品功能。 |
| **坑** | 别把"可信度"做成一个黑箱分数。**评审会问"为什么是 0.73"**，答不上来就白做。分数必须是**可分解的加权项**，能打印出贡献明细。 |
| **证据强度** | ★★★ 综述论文，方法体系清晰 |

### 1.4 上下文工程（Context Engineering）

| 项 | 内容 |
| --- | --- |
| **代表实现** | Anthropic《Effective Context Engineering for AI Agents》；compaction（上下文压实）、just-in-time retrieval、tool clearing、prompt caching 等实践在 2025-2026 已收敛成共识 |
| **适用场景** | 我们的 AI 管线本身就是一条多步 Agent 链（抽取 → 去重 → 核查 → 生成 → 推荐），每一步都在烧 token |
| **核心优势** | 直接对应三件事：**成本**（有实测报告称 prompt 缓存可降输入成本 41%~80%，Anthropic 官方称最高约 90%）、**稳定性**（上下文一长模型就开始丢指令，即 "context rot"）、**可维护性**（上下文是"按需组装"的，不是一次塞满）。 |
| **可借鉴的具体点** | ① **给管线设 Token 预算**：低信号内容进窗口前先裁剪，历史/检索的配比有个稳妥起点（约 35% / 65%）；② **把"校园静态知识"（校规、办事流程、POI 列表）放进缓存前缀**，动态内容（用户上报）放后面——**顺序错了缓存全失效**；③ **长会话用 compaction 而不是截断**：把前面的对话压成摘要，**摘要里必须保真的东西要显式列出来**（地点、时间、决定），否则会像某些开源 agent 一样"压实之后记忆全丢"；④ **工具不要全挂上**：一个挂 30 个工具的 Agent 通常不如挂 6 个精准工具的 Agent。我们的后端接口应该按"这一步用得上"动态暴露。 |
| **坑** | ★★ 长上下文窗口（1M 级）**不是免死金牌**，"lost in the middle" 依旧存在。别因为窗口大就不做预算管理。 |
| **证据强度** | ★★ 厂商官方文档 + 社区实测，数值需按自己场景复测 |

### 1.5 地点短语 → POI 锚点匹配

| 项 | 内容 |
| --- | --- |
| **代表实现** | MultiModal-LLM-POI-Match（2025，深度学习 POI 匹配开源方案）；学术侧对应 ACL 2026 的 POI 推荐与空间推理方向 |
| **适用场景** | "**三食堂二楼**" / "**图书馆门口那棵大树底下**" → 匹配到地图上的确定锚点，才能打点 |
| **核心优势** | 这是**我们独有的低成本杠杆**：设计任务书 D9 已经要求"食堂/教学楼/操场/宿舍/图书馆等主要人流节点预埋定位锚点"，建模阶段已产出 `ANCHOR_*` 对象。**锚点表就是天然的受控词表**，比任何通用地理编码都准。 |
| **可借鉴的具体点** | ① **混合匹配三级**：`精确/别名命中` → `句向量相似度` → `LLM 消歧（给定候选列表二选一）`；② 给每个锚点维护**别名表**（三食堂 / 第三食堂 / 3 食堂 / 三食），这一步人工做比模型做准；③ **匹配失败要能兜底**：落到"校区级"模糊位置并降低可信度，**绝不瞎猜坐标**；④ 把"楼层/室内方位"作为**锚点下的二级字段**，不参与坐标计算（虚拟定位场景下我们只需要"在哪个点"）。 |
| **坑** | ★★ 别上通用地理编码 API。校园内部 POI（三食堂二楼）在公网地图数据里根本不存在，调了也是错。**自建锚点表 + 别名表**是唯一正确解。 |
| **证据强度** | ★★ 开源实现 + 我们自己的资产现状 |

## 2. P1 · 3D 呈现的性能与格式

### 2.1 three.js：WebGPU 渲染器 + TSL + BatchedMesh

| 项 | 内容 |
| --- | --- |
| **代表实现** | `three/webgpu` 的 `WebGPURenderer`（自动 fallback 到 WebGL）、Node Material / TSL（Shader Graph → 自动生成 WGSL/GLSL）、`BatchedMesh`、`InstancedMesh`、Render Pipeline（Render Pass / Compute Pass / Post Effect Pass） |
| **适用场景** | 我们的 `preview.html` 全园预览页（153 万面、7 个机位预设） |
| **核心优势** | 2025-2026 的更新是**架构级**的，不是 API 微调：① WebGPU 带来 GPU compute（粒子/流体/实时物理）；② TSL 让 shader 跨 WebGL/WebGPU 一份代码；③ `BatchedMesh` 把多个不同 mesh 合成少数 GPU 调用——**这正好治我们的 draw call 病**。 |
| **可借鉴的具体点** | ① **先量后改**：我们已实测远机位 `drawn 307 万 → 153 万、calls 788 → 396`，主因是**阴影 pass 每帧重算**（`shadowMap.autoUpdate=false` 直接腰斩）——**任何新页面先跑同一套计数，再谈优化**；② 把"大量重复构件"（树、灯柱、栏杆、行道树）**全部走 InstancedMesh**；③ 用 `BatchedMesh` 合并**不同几何但同材质**的建筑构件；④ 分级策略继续用 `?quality=high\|balanced\|perf`；⑤ **WebGPU 可以先不上**——自动 fallback 存在，但移动端 WebView 的 WebGPU 支持仍不稳定，**上之前必须实测目标机型**，不能看桌面数据下结论。 |
| **坑** | ★★ 量性能有三个陷阱（异步 draw 会报假 60fps / `gl.finish()` 只信计数不信耗时 / 必须同机位 A/B），已在 skill 里记过，不再重复踩。 |
| **证据强度** | ★★★ 官方文档 + 我们自己的实测数据 |

### 2.2 glTF 2.1 / KHR_gaussian_splatting / SPZ / 3D Tiles 2.0 —— 2026 的标准化窗口

| 项 | 内容 |
| --- | --- |
| **代表实现** | Khronos 2026-06-11 公布 **glTF 2.1** 计划（面向复杂大场景，向后兼容）；glTF **`KHR_gaussian_splatting`** 扩展 2026-02 进入候选发布阶段（NVIDIA / Google / Adobe / Cesium 已对齐）；配套 **`KHR_gaussian_splatting_compression_spz`**（采用 Niantic 开源的 **SPZ** 格式，量化+gzip，比标准 PLY 小最多 90%；SPZ 4 于 2026-05 发布，约小 10 倍、取消 1000 万点上限）；OGC 于 2026-06-30~07-23 就 **3D Tiles 2.0** 公开征求意见；Cesium 2026-04-27 把 3DGS 正式纳入 3D Tiles（CesiumJS 1.139 起实现，1.144 于 2026-08-01 修了一批 SPZ 解码与千万级泼溅的 WebGL 问题） |
| **适用场景** | 我们导出的 `山河大学_全园_R7.glb`（5.70 MB / 153 万面）与后续任何三维交付 |
| **核心优势** | **格式标准正在换代，且换代方向对我们全是利好**：① glTF 2.1 专门面向"复杂大场景"，正是全园级模型的痛点；② 高斯泼溅进 glTF = **Web 原生可用**，进 3D Tiles = **地理参考 + 流式 LOD**；③ SPZ 把体积压到 PLY 的 1/10，移动端带宽才够。 |
| **可借鉴的具体点** | ① **守住基线**：导出必须满足「标准 glTF 2.0 + `KHR_draco_mesh_compression` 或 `EXT_meshopt_compression` + `KHR_texture_basisu`(KTX2)」——这三件事做对，未来换任何渲染后端都不返工；② **`KHR_gaussian_splatting` 不进关键路径**，但**要在方案书里作为"技术演进路线"写出来**（"我们的资产格式可平滑升级到 3DGS/3D Tiles 2.0"），这是实打实的创新性素材；③ 若未来要接 Cesium/3D Tiles，**现在就要给模型加真实地理参考**（哪怕只是相对坐标系约定），事后补会很痛。 |
| **坑** | ★★ 2026 年的标准还在走流程（候选发布 / 公开征求意见），**别在 40 天内押注未定稿格式**。策略是：**基线用稳的，叙事用新的。** |
| **证据强度** | ★★★ Khronos / OGC / Cesium 官方公告 |

### 2.3 3DGS 实景重建（仅「真实校园骨架」路线需要）

| 项 | 内容 |
| --- | --- |
| **代表实现** | 训练侧：`gsplat`（Nerfstudio 团队，内存优化 CUDA 内核，训练显存可低至标准实现 1/4，4 GB 显存可跑）、Nerfstudio、Lichtfeld Studio；采集侧：**Scaniverse**（Niantic，完全免费、**设备端训练**、导出 GLB/USDZ/PLY/SPZ）、Polycam、Luma AI、Kiri Engine；切片/压缩：**SuperSplat**（PlayCanvas，MIT，浏览器端）、SPZ 格式族、Cesium 3D Tiles；Web 渲染：**gsplat.js**（HuggingFace）、**Spark.js**（World Labs，MIT，2026-04 发布 2.0，支持 LoD Splat Tree / `.RAD` 流式 / GPU 虚拟内存分页）、**three.js 原生 GS 加载**（2026 年官方示例目录已加入）、GaussianSplats3D（mkkellogg） |

| **可借鉴的具体点** | ① 若做真实校园 Demo，**零成本路径**：`Scaniverse 拍 → SuperSplat 清 → gsplat.js/Spark.js 上 Web`，全程免费无云依赖；② **移动端预算参考值**：移动端控制在 **300 万高斯以内**、桌面 500 万以内；RTX 3060 级 + SPZ 4 压缩下，100 万高斯可稳定 60 fps（100 万高斯在 RTX 3070 上约 180-220 MB 显存、每帧 3-8 ms）。**这些是桌面显卡数据，中端手机要再打 3~5 折估。**；③ 压到 1/10 体积靠 SPZ 4；④ 标准化利好：进 glTF 即 Web 原生，进 3D Tiles 即流式 LOD。 |
| **坑** | ★★ 3DGS 与 mesh **不是替代关系**：泼溅不能做碰撞、不能编辑、不能打锚点。**正确用法是"泼溅做背景皮肤 + mesh 做交互体"**，两者叠加（Spark.js 明确支持与 three.js mesh 管线融合）。 |
| **证据强度** | ★★ 工具链开源可复现；性能数字为社区实测，非官方 |

### 3.2 生成式推荐与语义 ID（**必须降级使用**）

| 项 | 内容 |
| --- | --- |
| **代表实现** | **OneRec**（快手，2025-02，端到端生成式框架，Session-wise 生成替代级联漏斗；落地全量后**用户观看时长 +1.6%**，MFU 达 28.8%）；**OnePiece**（腾讯，2025-12，统一 Encoder-Decoder，**协同 Tokenizer + 残差 K-means 量化把 Hash 冲突率降至 7.86%**，验证语义生成与嵌入检索均遵循幂律缩放）；**Jagged CP for HSTU**（Meta，2025-08，序列长度 3072→16384，峰值显存降 >60%，吞吐升 >2 倍）；**MACRec**（美团，AAAI 2026 Oral，跨模态量化生成低冲突语义 ID）；**CRAVE**（Netflix，**EMNLP 2025 最佳论文**，协同语言化经验 + **双代理辩论**）；**REGEN**（Google，2025-06，合成批评数据 + 统一多任务生成） |
| **适用场景** | 事件流/帖子的个性化排序；冷启动（新用户没有行为数据） |
| **核心优势** | 思想层面：**用语义 ID 把 item 变成"可生成的 token"，冷启动和跨模态都变简单**；工程层面：**Hash 冲突率是语义 ID 的核心痛点**，2025 年一整年的论文都在解决它。 |
| **可借鉴的具体点（关键：降级）** | ⚠️ **不要照搬 OneRec/OnePiece 的端到端架构**——那是 4 亿 DAU、亿级 item 的场景。我们该抄的是三件轻量的事：① **用 LLM embedding 做 item 语义表示**，再用简单聚类/量化生成"语义标签"，用于冷启动匹配（新用户选 3 个兴趣标签 → 直接匹配语义相近的事件簇）；② **抄 CRAVE 的"语言化经验 + 双代理辩论"做推荐理由生成**——两个 Agent 分别主张"该推"和"不该推"，辩论结果作为推荐解释，**这个方案在我们这个数据量下完全可行，而且"可解释的推荐"是很好的创新点**；③ **评测口径**：离线看 Recall@K / 多样性，别只看准确率——社区产品推同质内容会死。 |
| **坑** | ★★★ 语义 ID / 端到端生成式推荐**对数据量的要求是硬门槛**。我们连 1 万条交互都未必凑得齐，**上这个架构必然过拟合或根本训不动**。方案书里可以写"已验证语义 ID 在冷启动上的可行性"，但不能写"我们实现了端到端生成式推荐"。 |
| **证据强度** | ★★★ 论文与工业落地数据齐全；但**落地条件与我们的量级不匹配** |

### 4.4 RAG 评测体系（Ragas）

| **适用场景** | 填上一直空着的 `03-算法工程/04-评测/` |
| **核心优势** | 竞赛评分里「技术实现 20 分」和「方案完整性 20 分」都吃"有没有量化评测"。**这是最低成本把评测目录填满的方式**，而且能直接产出图表。 |
| **可借鉴的具体点** | ① **三层评估**：检索层（Context Precision/Recall）→ 生成层（Faithfulness）→ 端到端层（任务成功率）；② **对我们的关键改造**：把"事件抽取准确率"（地点/类型/时间三字段的 F1）作为端到端指标——**这是最能打动评审的数字**；③ 评测集人工标 200 条就够起步，**不要等大而全**；④ 评测报告直接进 `05-测试与质量/`。 |
| **证据强度** | ★★★ 开源框架，被广泛采用 |

### 4.5 CRDT 实时协作（Yjs）

| 项 | 内容 |
| --- | --- |
| **代表实现** | **Yjs**（开源 CRDT 框架）；CRDT vs OT 的选型共识在 2026 已比较清晰 |
| **适用场景** | 多人协作标注地图（学生共同维护某个区域的描述/标注），对应产品定位里的"**可共创**" |
| **核心优势** | 无需中心协调即可解决冲突，**弱网/离线场景下比 OT 更稳**——校园网络环境恰恰是弱网场景。 |
| **可借鉴的具体点** | ① 如果要做"共创地图"，**只在标注层用 CRDT**，事件数据本身走常规后端；② 这属于**锦上添花**，40 天里优先级应排在 P0/P1 之后。 |
| **证据强度** | ★★ 成熟开源框架 |

## 5. 明确不建议跟进（反面清单）

| 方向 | 为什么不做 |
| --- | --- |
| **SDS / DreamFusion 系的"蒸馏式"3D 生成** | 每样本优化数十分钟到数小时，且系统性的过饱和与 Janus 多头问题。**已被后续路线淘汰，没有理由回头。** |
| **自研 3D 生成基础模型** | 训练数据量级差三个数量级（全球精选 3D 资产几十万 vs 文本百亿级）。**这不是努力能补的差距。** |
| **端到端生成式推荐（OneRec/OnePiece 级架构）** | 数据量不够，必然过拟合或训不动。**只借鉴思想，不照搬架构。** |
| **动态 4D 高斯泼溅** | 我们没有动态场景需求；且该方向 2026 年虽最密集，但"可跟踪/保真/实时/省存储"四者只能选三。 |
| **世界模型（Genie 系 / Cosmos / HunyuanWorld）** | 无显存、无数据、无场景。**最多作为方案书"技术展望"里的一句话。** |
| **真实 GPS 定位追踪 / 摄像头 AI 轨迹 / 视频孪生** | 需求基线已明确选择**虚拟位置**（零硬件依赖、合规风险归零）。**校园场景下的学生轨迹采集是伦理与法律双重雷区**，竞赛周期内不值得碰。 |
| **视觉定位 VPS（EasyAR Mega / Niantic VPS 2.0 / 网易易现）** | 技术本身很成熟（厘米级），但需要真实场景采集 + 硬件依赖。**我们已选虚拟定位，这条只作为"未来规划"一句话带过。** |
| **把可信度做成黑箱分数** | 不可审计、不可复现、评审一问就崩。**必须可分解。** |
| **在 40 天内押注未定稿的 3D 标准** | glTF 2.1 / KHR_gaussian_splatting / 3D Tiles 2.0 都还在走流程。**基线用稳的，叙事用新的。** |

## 7. 建议的落地顺序

1. **第 1 步（1 周）**：定义事件 Schema + 接入约束解码 → 跑通「一句话变一个结构化事件」
2. **第 2 步（1 周）**：锚点表 + 别名表 → 跑通「文本地点 → 锚点 ID」，这是去重的前置
3. **第 3 步（1 周）**：三路融合去重（空间 150 m / 时间 45 min / 语义 0.78）→ 产出事件簇
4. **第 4 步（1 周）**：可分解的可信度评分 + 官方源 RAG 核查 → 安全类走人工闸门
5. **第 5 步（并行）**：评测集人工标 200 条 → 跑出抽取 F1 与去重准确率，填满 04-评测
6. **第 6 步（并行）**：three.js 渲染优化沿用已有配方；确认 GLB 满足 glTF 2.0 压缩基线
7. **第 7 步（有余力）**：GraphRAG 办事引导 / 人流预测基线 / 端侧小模型初筛

> ★ 每一步完成即汇报，确认后再进下一步（沿用项目既有节奏）。
> ★ 前 4 步是**关键路径**，任何一步没跑通都不要往下走——这四步就是产品能不能成立的分界线。

## 8. 调研方法与局限（诚实说明）

- **证据分级**：★★★ = 官方标准/论文原文可查；★★ = 开源可复现或社区实测；★ = 二手转述，需自行验证。**本报告中标注为"自评/官方声明"的性能数字，均未经第三方独立验证。**
- **语言偏置**：本次调研的中文资料占比偏高（中文技术博客对 2026 年生态的转述较新），**部分性能数字来自二手转述**。凡涉及"提升 N 倍"的表述，本报告已尽量标注来源性质。
- **未覆盖**：iOS 端 WebView 的 WebGPU 实际支持情况、Flutter 原生 3D 渲染（Filament/Impeller）的可行性、具体云服务选型与成本测算——这些属于工程实施层，建议在技术栈确定后另做专项。
- **时效提示**：3D 格式标准（glTF 2.1 / 3D Tiles 2.0）与 MCP 规范均在 2026 年内有变动，**定稿前建议复核官方公告**。
