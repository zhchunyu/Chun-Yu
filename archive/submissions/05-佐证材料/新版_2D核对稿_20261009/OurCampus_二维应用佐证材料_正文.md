# 先核对地点 再提供操作
优势一 地点可靠

“模型给了一个地名”不等于“用户说的是这个地方”。当前系统仅接受原文可明确匹配的地点，或用户手动选择的地点。无地点时留空，多地点时提示选择。

![图3 错误地点注入实验  直接采信一侧为处理方式模拟](D:\project\college\26_10_8_college\06-竞赛材料\05-佐证材料\新版_2D核对稿_20261009\图示素材\wrong_place.png)

原始注入内容和实际接受结果见评测包。模型的摘要与建议仍需在线检查；地点核对通过不代表整段文字没有错误。

# 回答前先准备校园资料
优势二 资料辅助

校园问题需要具体资料。当前处理链向AUV传入地点、服务及可取得的有效动态，并要求未知信息保持未知；动态读取失败会另作提示。

60/60项离线资料传递检查通过。这里的模型回复为占位内容，只验证资料怎样进入请求；真实回答是否准确，留待180条在线质量题及人工评分。

<!-- PAGE 6 -->
# 不是每条消息都交给模型
优势三 按需处理

紧急情况先显示应急联络提示；失物和互助信息转向适合的渠道；校园事件再交给AUV整理。处理方式与用户任务一致，比统一生成一段回答更便于继续操作。

![图6 典型消息的处理路径与已发现的否定句缺口](D:\project\college\26_10_8_college\06-竞赛材料\05-佐证材料\新版_2D核对稿_20261009\图示素材\routing.png)

分流测试36/40项通过。应急提示在登录校验之后触发，不能替代电话求助或紧急服务；当前否定与转述句仍会出现误触发。

<!-- PAGE 7 -->
# 出错时也要让用户知道发生了什么
运行可靠性

可靠性不仅是“返回一句话”。未登录、失效地址、错误格式、频率限制和上游失败，都应返回可理解的提示，并保护输入和服务配置。

![图7 当前网关与客户端的异常处理设计](D:\project\college\26_10_8_college\06-竞赛材料\05-佐证材料\新版_2D核对稿_20261009\图示素材\errors.png)

20/20项可控协议及故障注入检查通过；原有网关8个测试用例全部通过。故障由测试程序制造，不是线上长期可用率或压力测试。

# 把不同处理方式放在同一任务下
方案比较

表6 技术路径的机制对照
| 任务 | 单一处理方式 | 当前组合方式 |
| --- | --- | --- |
| 地点不明确 | 直接采用输出地点会引入误定位风险 | 地点留空或让用户选择 |
| 口语说明 | 固定表单要求用户自行拆字段 | AUV整理，地点另行核对 |
| 查询校园资料 | 不提供资料时缺少校园依据 | 先准备资料，缺失状态单独提示 |
| 回答后的操作 | 文本需要用户另找入口 | 地点卡片连接查看与导航入口 |

当前可识别的应用改进，是把语言理解、地点核对和地图操作接在一起。各环节保留不同职责，减少模型输出直接成为地点事实的机会。

这是机制比较，不是实际竞品评测。外部产品、文献和专利检索尚未完成，因此不使用“国内首创”“全球领先”或竞品准确率。检索方法见补证清单。
