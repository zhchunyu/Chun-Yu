## 本轮踩到并修掉的坑
- **纵梁写成了"每段一个 1 m 方块"（段长 3 m）→ 整条纵梁断续**，渲出来是桥下一排"暗色牙齿"。
  根因：用 `box(_mx, _my, _BEAM_W, _BEAM_D, _BEAM_D, ...)` 逐段生成，宽度取的是**段长**而不是"梁宽沿法向"。
  修法：纵梁必须**沿路径连续**，按 `offset_loop` 生成整条带，不能逐段 box。
- **"七个站点在图上读不出来"** → 站点不能只靠"加宽站台 + 立柱"，必须**改变廊身本身的节奏**：
  格栅在每个站点**断开成门洞** + **一对铜柱**框住，站台加宽到 18 m。改完一眼就能认出节点。
- **铜檐口线过粗**（0.34 → 0.25×0.16）；**木肋嵌进壳里的位置不对**（`lift` 要传壳厚，同 R3 坑 29）

## 四条结论（R5~R7 沿用）
1. **"云廊"的断面高度必须够**：跨 14.6 m 配矢高 3.20 m，檐下净高才 4.20 m。
   v1 用 2.95 m 净高 → 整条廊读成"一块扁板扣在桥上"。**廊之所以是廊，靠的是檐下那段空**。
2. **节点的可读性来自"廊身节奏的中断"**，不是来自"加东西"。
   加宽站台 / 加立柱都是在既有节奏上叠东西，图上读不出来；**把格栅断开成门洞**是中断节奏，立刻可读。
3. **环形构筑物的"里外"必须用几何判定，不能用绕向符号**（`ring_at` 的向外法向用"背离形心"）。
   一旦谁调整了 `RING` 顶点顺序，内外侧会静默对调（栏板跑到里面、格栅跑到外面），而且不报错。
4. **超长线性构件（纵梁 / 檐口线 / 扶手）一律"沿路径连续生成"**，禁止"逐段 box"。
   逐段 box 只要段长 ≠ 构件宽度，就必然出现断续或错位，且渲染出来只是"看起来有点怪"。

## 本轮踩到并修掉的坑
- **`put(B, mat, service_shaft(...))` 报 `not enough values to unpack (expected 2, got 1)`**
  根因：`service_shaft()` 返回的是**按材质分桶的 dict**，不是几何列表。
  `put()` 把整个 dict 当成一个几何塞进列表 → 到 `emit_to` 里 unpack 就炸。
  **规则：凡返回 dict 的构件一律走 `merge()`，只有返回"几何列表/单个几何"的才走 `put()`。**
- **`教学区_近景` 机位渲成整张纯黑（100% 暗）**：机位落在物体内部。
  → 必须用 `_diag_cam.py` 打射线确认机位，不能凭坐标"觉得"它对着目标。
- **坐标映射必须实测，不能猜**：一度以为 `W()` 是 `(svg−340)×2.4`，
  实测 `W(340,516)→(0,0)`、`W(0,0)→(−816,1238.4)` 才确认
  **世界 = ((svg_x − 340) × 2.4, (516 − svg_y) × 2.4)**，场地世界范围 X[−816,816] Y[0,1238]。
  排查过程中因为猜错映射，白跑了两轮机位诊断。
- **`_diag_cam.py`（新增诊断脚本）**：一次打印 (a) `W()` 若干已知点的双向换算、
  (b) 关键对象的**世界包围盒（中心 + 顶高）**—— 用来核对天际线是否真的错落、
  (c) 每个机位 5×3 网格射线的**首个命中物 + 距离** —— 用来核对机位是否真的对着目标区。
  比 AABB 查询可靠，比"看截图猜"快得多。

## 四条结论（R6~R7 沿用）
1. **"色彩不对"先查环境光，别查材质。** 天空贴图同时充当"可见天空"和"环境光"时，
   可见天与照明必须解耦（`sky_visible` / `ambient_tint`），否则背光面永远被染成天空的颜色。
2. **压金属度不够，还要提粗糙度。** 屋面接近水平，掠射角下菲涅耳反射很强 ——
   实测把钛锌 metallic 从 0.60 压到 0.15，成图**几乎没变**；roughness 提到 0.80 才动。
3. **"远看全是平房"是体量问题，不是高度问题。** 一栋楼必须自己就有 2~3 个标高
   （裙房 + 多个不同高度的主体量，各自女儿墙收头），单靠"把整体拔高"没有用。
4. **凡返回 dict 的构件必须 `merge()`，不能 `put()`。** 这条错误只在 `emit_to` 里报，
   报错信息（unpack）与真实原因（构件返回类型）完全不相干，很难反查。

# 悬空铜环定位与修复（R5 第 6 版成图的"飞线"）

## 症状
`R5_教学区_近景` / `R5_科技区_近景` / `R5_生活区_沿街` 等成图里，
屋顶上方漂着一圈**细铜线**，像"铁丝网 / 呼啦圈"，且甩到画面外。

## 诊断链（**三次走错路，值得记下来**）
1. ✗ **射线打点**（`diag_ray.py`）：细杆件只有 2~4 px 宽，单点射线全打偏 →
   先改用纯 Python 从成图里**算出**橙色像素的密集区，再打射线 → 命中
   `BLD_教学_公共教学楼_铜饰`，但**光有对象名定不了位**
2. ✗ **手算中心**：第一次用 `Z(462,378,...)` 推的中心 `(280.8,321.2)` —— 错。
   量出来裙房中心是 `(292.8,331.2)`，主体量相对裙房**有 (dx,dy)=(-12,-10) 偏移**。
   中心错了 → 得出"铜饰半径 63 超出壳半径 34、飞出去了"的**假结论**
3. ✓ **按材质隔离渲染**：`jobs[]` 不认 `iso_keep`，要走 `build_extra` 通道挂一个
   `_iso.py`（读 `ISO_KEEP` 环境变量设 `hide_render`）→ 铜饰单独出图，
   **悬空环一眼可见**
4. ✓ **bmesh 拆连通块 + 逐块量 bbox** → 找到 `gi=220/202`：
   `X[252.2,309.4] Y[293.6,347.2] Z[46.3,48.2]`

## 根因
`build_campus_r5.py` 的 `hip_shell()` 封顶分支：

```python
put(B, M_ZINC,   box(cx, cy, 2*hx*s_min*0.96, 2*hy*s_min*0.96, 0.34, _zt-0.34))  # 板：缩了
put(B, M_COPPER, rim_edge(prof, zf, s_min, 0.34, r=0.20))                        # 环：没缩
```

**`rim_edge` 不做轮廓缩放**，而 `shell_solid` / `shell_ridges` 都是
**按 `prof` 形心缩放**。于是这一圈铜环：**标高按 `s_min` 算（≈壳顶 47~48）**，
**平面却是全尺寸轮廓（檐口 57.0×55.0）** → 悬在檐口上方 6 m 的"铜呼啦圈"。
环的 `Z` 还随 `tilt_y` 从 46.3 斜到 48.2，与 `zf(s_min)` 完全对得上 —— 一读就实了。

## 修法（**对齐约定，而不是打补丁**）
改 `build_campus_r2.py` 的 `rim_edge`：轮廓**按 `s` 绕形心缩放**，
与 `shell_solid` / `shell_ridges` 同一约定。
全项目 `rim_edge` 调用只有 4 处，其余 3 处都是 `s=1.0` → **数学上完全等价，零回归**
（R2 图书馆 / R2 漂浮讲堂 / R3 大礼堂都不用重渲）。
docstring 里写明"`s=1.0` 是外缘收边、`s=s_min` 是封顶压环"。

## 31 图集在手机上打不开 / 图片不显示（用户反馈）

**现象**：用户反馈①无法打开网页版界面 ②手机上查看建模图集时图片无法正常显示。

**根因**：图集引用的是 `../renders/*.png` **相对路径**，而本项目从工作区目录到图片文件名
**全是中文**。两类现实问题：
1. 非 ASCII 路径在不同 HTTP 服务下编码处理不一致 ⇒ **静态预览 / 手机浏览器里图全裂**（页面不报错）
2. 只把 HTML 发到手机 / 转给别人 ⇒ `renders/` 根本不在旁边 ⇒ 必然缺图

**修法**（两条一起做，覆盖两种用法）：
- **主图集**：①所有图片 URL 走 `urllib.parse.quote()` **百分号编码**；
  ②补 `<meta name="viewport">`（原先没有）；③加窄屏媒体查询（原 `.page` 固定 1120 px 宽，
  手机上必然横向溢出）；④表格包 `.tw{overflow-x:auto}` 让宽表格可滑动
- **新增单文件手机版** `山河大学_三维建模图集_手机版.html`（`scripts/make_atlas_mobile.py`）：
  图片缩到 1000 px / JPEG q84（实测 ~86 KB/张）**内嵌为 base64 data URI** ⇒
  **单文件 1.9 MB，不依赖任何外部文件**，可离线、可单独转发、可随意改名。
  ★ **文案只维护一份**：手机版脚本直接 `import make_atlas_html` 复用 `STAGES`/`METRICS`
- 起本地服务 `python -m http.server 8130 --bind 127.0.0.1`（根目录 = `02-三维资产/`），
  相对路径即成立 —— 这是"最接近网页版"的打开方式

## 32 新增 `tools/_measure_layout.cjs`（Playwright 版式体检）

**为什么必须有它**：`--headless=new --screenshot` **只给一张图**，
看不出"文字被右边缘切掉"到底是**正常换行**还是**布局宽度超视口**。
更坑的是：**Edge 在窄窗下会在较宽视口渲染再裁切** —— 实测 `--window-size=390,900`
截出来的图看起来"文字被切"，但 Playwright 量出 `scrollWidth == clientWidth == 390`，
**布局其实完全正常**。⇒ **判断窄屏版式一律用 Playwright，别用 Edge 截图**。

输出三项：**图片加载数**（"图片不显示"的唯一可靠判据，靠 `img.naturalWidth > 0`，
且要先滚到底触发懒加载）、有无横向溢出、所有比视口宽的元素
（标注 `[可滚动]` / `[!溢出]`，前者在 `overflow:auto` 容器里属正常）。

实测结果：主图集与手机版 **@390 px 均为「图片 24/24 加载 + 无横向溢出」**。

## 33 教训
★ **"交付给别人看的东西"不能依赖相对路径 + 中文文件名**。
自包含（内嵌资源）是唯一在各种设备 / 各种预览器下都成立的做法。
代价只有体积（1000 px JPEG 内嵌后 1.9 MB），完全可接受。
★ 每次做 HTML 交付物，**都要问一句"这个文件单独拷走还能看吗"**。
