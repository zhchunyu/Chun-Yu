# 实时数据怎么进到 AI 里 —— 数据流与边界

> 结论先行：**实时数据必须进到 AI 的输入里**（否则它答不了"三食堂现在排队多久"）。
> 但**搬运数据的是后端**，不是 AI 服务自己去查库。

---

## 0 先把「连接」这个词拆开

| 「连接」的两种含义 | 要不要 |
|---|---|
| **数据流动**：数据库里的实时状态要进入 AI 的输入 | ✅ **必须** |
| **凭据连接**：给 AI 服务一个数据库连接串，让它自己执行 SQL | ❌ 不要 |

### ★ 关键事实：大模型不会自己查库

它是**无状态函数** —— **文本进、文本出**。没有"记忆"，也没有"查询"能力。

所以「AI 读数据库」这个动作，**实际执行者是后端**：
后端查完 → 把结果**拼进 prompt** → AI 才有得读。

```
数据库（事件表 / 地点表）
      ↓ 后端查询（SELECT）
业务后端（查库 + 拼 prompt）
      ↓ 把数据写进 messages
AI 服务（无状态 · 不查库）
      ↓ 生成回答
学生看到
```

---

## 1 正确形态：后端做「检索 + 拼装」

```
用户问："三食堂现在人多吗"

后端：
  ① 查库 → { 三食堂: 排队 20 分钟(16:35), 图书馆: 座位剩余 40%(16:30) }
  ② 拼 prompt：
        【当前校园实时状态】
        三食堂：排队约 20 分钟（16:35 更新）
        图书馆：座位剩余 40%（16:30 更新）

        用户问：三食堂现在人多吗
  ③ 发给 persona 模型
  ④ 模型回答："三食堂现在排队大概二十分钟，比平时久，要不先去谷园餐厅看看？"
```

★ 这个模式叫 **RAG**（检索增强生成）—— **检索在后端，生成在模型**。

---

## 2 为什么不让 AI 服务自己连库

技术上可行（挂 MCP / tool-calling 让模型生成 SQL），但**为了省一件事，引入四件麻烦**：

| | 后端查库 → 拼 prompt（推荐） | AI 服务自己连库 |
|---|---|---|
| 库凭据 | 不离开后端 | ★ **要交给一个公网暴露的服务** |
| SQL 可控性 | 后端写死的查询，**只读** | 模型现生成的 SQL，**不可控** |
| 延迟 | 一次往返 | 每次多一轮（模型先"想"查询再执行） |
| 并发 | 后端连接池统一管理 | ★ AI 服务**无状态** ⇒ 多请求并发时状态混乱、连接池耗尽 |
| 审计 | 查了什么全在后端日志 | 无法审计 |

### 什么时候才需要 tool-calling？

当**「要查什么」取决于模型的多轮推理**时 —— 比如让模型连续查 5 次库做归因分析。

**本项目是单次查询**（问一个地点 → 查一条记录），后端查一次就够。

## 3 职责划分

| 角色 | 职责 | 明确不做 |
|---|---|---|
| **业务后端** | ① 意图分类 ② **查库**（实时状态 / 权威表）③ **拼 prompt** ④ 调 AI ⑤ 校验 + 落库 + 推送 | — |
| **AI 服务** | 只做**文本进 → 文本出**（`extract` 抽 JSON / `persona` 说话） | ❌ 不持有库凭据、不执行 SQL、不查表 |
| **数据库** | 事件表（实时状态）+ 地点表（权威表） | ❌ 不被 AI 服务直接访问 |

★ **核心认知：模型的输出是「候选」，不是「事实」。** 后端才是唯一有权写库的角色。

---

## 4 两条数据通路，都走后端

| 通路 | 方向 | 谁做 |
|---|---|---|
| **写入** | 学生上报 → 意图分类 → extract → 校验 → **后端落库** | 后端 |
| **读出** | 用户提问 → **后端查库** → 拼 prompt → persona → 回答 | 后端 |

两条通路**都在后端汇合**，AI 服务永远只在中间做一次"文本转换"。

---

## 5 三条红线

1. **AI 服务不持有任何数据库凭据** —— 它是公网暴露的、无状态的
2. **`building_name` / `building_id` 必须经权威表校验后才能用** —— 查不到就丢弃，退回发帖人 GPS
3. **`severity` 别信模型** —— 实测三路全 5/10，是标注口径问题 ⇒ 给死规则或砍掉

---

## 6 常见误解对照

| 误解 | 实际 |
|---|---|
| "AI 连上数据库就能答实时问题" | 模型不会查库，得**后端把数据放进 prompt** |
| "把权威表塞进 prompt 让模型认地名" | ❌ 方向错了 —— 查表微秒级且 81%，塞 prompt 秒级且更差 |
| "让模型直接写事件表" | ❌ 绝不要 —— 模型没权限、没事务、会写脏数据 |
| "省掉后端这一层" | ❌ 省不掉 —— 意图分类、查库、拼装、校验都是**后端逻辑** |
| "AI 服务要一直开着才叫'连着'" | 它是无状态服务，**每次请求自带上下文**，不存在"连着"这回事 |
