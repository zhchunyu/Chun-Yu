## 0. 一句话结论

安全管理模式**不是一个功能，而是一层视角**——同一张地图、同一套路网、同一套事件管线，
换一个「以风险为中心」的读法。所以它不该做成一个孤立页面，而应该是**贯穿全局的安全图层 + 预警中枢**。

**两条★旗舰亮点**（其余路线都是为它们服务的）：

| # | 亮点 | 为什么是亮点 |
| --- | --- | --- |
| ★1 | **预警 ↔ 路网双向联动** | 预警一发布，路线自动绕行；处置一完成，路线自动恢复。**把"报警"和"调度"合成一个动作** —— 这是市面上绝大多数校园安全系统做不到的，因为它们的安全模块和导航模块是两套东西 |
| ★2 | **可信度闸门 + 证据链可解释** | 安全类事件低于阈值**不自动打点**，进人工审核队列，且**每一分都能打印贡献明细**。直接对应赛事评分「AI 算法设计科学」与需求基线 §九 点出的法律责任边界 |

## 3. 路线 A · 人流量最大阈值风控

### 3.1 要解决的真问题

现在的人流是**枚举**（`low / normal / busy`），只能显示颜色，**做不了风控**。风控需要三样东西：

1. **数值**（能比大小、能算趋势）
2. **阈值**（每个地点的容量不一样，食堂和操场的阈值差一个数量级）
3. **防抖机制**（否则告警会响成背景噪音，最后所有人都不看了）

> 💡 这一条是安全风控里**最容易被做废**的地方。绝大多数方案止步于「超过阈值就报警」——
> 那结果一定是第一天报警 200 次、第二天开始没人看。**把防抖做对，才是"设计过的风控"。**

### 3.2 数据模型改造

```js
// src/domain/crowd.js （新建）
// 把枚举升级为「数值 + 基线 + 容量」，枚举降级为派生视图（向后兼容，不破坏现有 UI）
export const crowdReading = {
  locationId: 'Canteen',
  count: 312,                 // 当前估算人数（路段吸附计数或闸机/信标数据）
  capacity: 400,              // 该地点安全容量（人工配置 + 可管理者调整）
  ratio: 0.78,                // count / capacity
  baseline: 0.45,             // 近 7 天同时段中位数（复用 §7 的基线机制）
  trend: +0.12,               // 近 3 个时间片斜率（正在涨还是正在落）
  ts: 1774000000000,
}
```

**关键设计：容量不是全局常数，而是按地点类型分档配置**

| 地点类型 | 容量口径 | 示例 |
| --- | --- | --- |
| 餐饮（食堂） | 座位数 × 1.2 瞬时容差 | 第三食堂 400 |
| 教学（教学楼/图书馆） | 消防疏散容量（**有法定依据**） | 图书馆 800 |
| 通行（路段/校门） | 单位宽度人流量（人/min/m） | 中轴大道 60 人/min/m |
| 集会（操场/广场） | 报备人数 × 1.1 | 操场 1500 |

> 「容量」这一项**必须有可解释的来源**——消防疏散容量、座位数、通道宽度都是有依据的。
> 评审会问「你的阈值怎么定的」，答「拍的」就完了，答「按消防疏散容量 + 通道宽度人流量」就立住了。

### 3.3 风控判定：分级 + 迟滞 + 驻留 + 冷却

```js
// src/domain/crowdRisk.js
export const RISK_LEVEL = { NORMAL:'normal', WARN:'warn', HIGH:'high', CRITICAL:'critical' }

// ① 双阈值迟滞（hysteresis）—— 上升用高阈值，回落用低阈值，杜绝阈值附近反复横跳
// ② 驻留时间（dwell）—— 必须连续 N 个采样片超限才成立，抑制瞬时尖峰
// ③ 冷却期（cooldown）—— 处置后 T 分钟内同一地点不重复告警
const RULES = {
  warn:     { up: 0.75, down: 0.65, dwell: 2, cooldown: 10 * 60e3 },
  high:     { up: 0.90, down: 0.80, dwell: 3, cooldown: 15 * 60e3 },
  critical: { up: 1.05, down: 0.95, dwell: 3, cooldown: 20 * 60e3 },
}

export function evaluateCrowdRisk(series, config, now) { /* 返回 { level, reason, evidence } */ }
```

**四个必须写进方案书的机制**（这是「技术实现 20 分」的可见设计）：

| 机制 | 不用它会怎样 | 用了它的说法 |
| --- | --- | --- |
| **双阈值迟滞** | 人数在阈值上下抖动 → 告警反复开关 | 「上升沿/下降沿分离，消除抖动」 |
| **驻留时间** | 一次瞬时尖峰就报警 | 「需连续 N 片确认，抑制瞬时噪声」 |
| **冷却期** | 同一地点重复推送，用户屏蔽 | 「告警去重 + 处置窗口」 |
| **趋势外推** | 只能事后知道挤了 | 「斜率转正即提前预置提醒」 |

### 3.4 空间聚合与传播（★ 差异化点）

**不要只做「单点阈值」，要做「空间传导」** —— 这是从「计数器」升级到「风控系统」的分界：

```
① 三级空间粒度
   格网（50 m 方）→ 路段（复用 109 条边）→ 建筑（复用 30 个地点）
   ★ 用「路段」而不是「格网」做桶 —— 路网已经有了，比格网更贴合（§7 已定）

② 拓扑传播
   某个路段拥挤 → 沿相邻边扩散预警：上游路口提前分流
   食堂拥挤 → 相邻路段 + 商业街 同步升档（人流溢出是空间相关的）

③ 天气修正系数（与路线 C 联动）
   雨天：室内地点容量 ×0.8（人待得更久）、室外 ×0.6
   高温：室外容量 ×0.5、室内 ×0.9（都往室内挤）
   ⇒ 「同一地点，晴天 75% 不报警，暴雨天 75% 要报警」——这才是真实的风控
```

### 3.5 可复用的落点

| 复用 | 用法 |
| --- | --- |
| `CROWD_STATUS` 枚举 | 保留为 `ratio` 的**派生视图**，现有 UI 零改动 |
| `MapLayerPanel.jsx` | 新增 `showCrowdHeat` / `showRiskZones` 两个开关（改 LAYERS 数组） |
| `HotspotLegend.jsx` | 图例补上**风险四色**（正常/关注/高/严重），补掉"图例有类别但没图层"的旧缺口 |
| `edgeCost()` 的 `congestion` 系数 | 风险等级直接喂给路段代价，**与路线 D 共用同一套系数** |
| §7 通行热度异常检测 | 基线（近 7 天同时段中位数）**同一套统计**，不要写两遍 |

**成本**：2 天 ｜ **前置**：修锚点表（§10 缺陷 1）+ 修可信度常数（评审 §3.1）

## 4. 路线 B · 事故突发预警

### 4.1 定位：把「信息流」升级为「处置流」

现在的事件是**内容**（发出来给大家看）。预警是**任务**（有人要去做事）。差别在于三样：
**分级、责任人、时限**。

### 4.2 分级矩阵：严重度 × 场所敏感度

```js
// src/domain/alert.js
export const SEVERITY = { INFO:'info', LOW:'low', MEDIUM:'medium', HIGH:'high', CRITICAL:'critical' }

// 事件类型 → 基础严重度（不走 AI，走规则，可解释、可审计）
const TYPE_BASE = {
  safety: 'high',      // 安全类：护栏松动、路灯损坏、地砖翘起
  traffic:'medium',    // 通行类：车辆占道、剐蹭
  service:'low',       // 服务类：快递积压
  notice:'info',       // 通知类
  help:'low',          // 互助类
}

// 场所敏感度倍率（★ 同样的火情，宿舍楼和操场不是一个级别）
const PLACE_WEIGHT = {
  dormitory: 1.5,      // 宿舍（夜间人员密集、逃生困难）
  laboratory: 1.5,     // 实验室（危化品）
  canteen: 1.3,        // 食堂（明火 + 燃气）
  library: 1.2,        // 图书馆
  sports: 1.0,         // 体育场馆
  road: 1.1,           // 道路（涉及通行安全）
}

// 时段权重：夜间（22:00–06:00）同级别自动升档 —— 夜间处置资源少、视野差
export function gradeAlert(event, place, ts) { /* 返回 { level, reason, evidence } */ }
```

> 💡 **「场所敏感度」是这一条最值得写进方案书的设计**。它把「AI 分类」和「校园空间知识」
> 真正结合起来了 —— 而绝大多数方案里，这两个是不相干的。

### 4.3 状态机落地（照抄 §6，不重新设计）

```js
export const ALERT_STATE = {
  REPORTED:     'reported',      // 上报
  EXTRACTING:   'extracting',    // 抽取中（AI 五步可见）
  PENDING:      'pending',       // 待核查
  VERIFYING:    'verifying',     // 待核实（灰标，不打点）★ 安全类专用分支
  PUBLISHED:    'published',     // 已发布
  DISPATCHED:   'dispatched',    // 已派单 ← 新增，预警与信息流的分界
  RESOLVED:     'resolved',      // 已处置
  CLOSED:       'closed',        // 已结束
  CONTRADICTED: 'contradicted',  // 证据矛盾 → 可信度回落
}
```

**四条分支必须都做到，且都要在演示里跑一遍**：

```
上报 → 抽取中 → 待核查 ─┬─ 可信度 ≥ 阈值 → 已发布 → 已派单 → 已处置 → 已结束
                        │                                        ↑
                        │                          处置结果回写可信度（闭环）
                        └─ 可信度低 或 安全类 → 待核实（灰标不打点）
                                                  │
                                        人工审核 ─┴─ 通过 → 已发布 ／ 驳回 → 已结束
                        ★ 证据矛盾（"现场已通过"）→ 可信度回落 → 自动解除封路 → 路线恢复
```

**★ 反向闭环「证据矛盾」是演示里最有说服力的一条路径**：事件发布后，另一个用户上报
「已通过 / 已清理」→ 证据矛盾 → 可信度回落 → **自动解除封路 → 路线自动恢复**。
这条路径同时演示了：多源交叉验证、状态机回落、路网联动解封。**一次演三个技术点。**

### 4.4 处置时限与升级（SLA 机制）

| 等级 | 响应时限 | 超时升级动作 | 升级到 |
| --- | --- | --- | --- |
| `critical` | **3 分钟** | 推送 + 短信 + 大屏闪烁 | 保卫处值班 + 校领导 |
| `high` | 15 分钟 | 推送 + 大屏常驻 | 保卫处值班 |
| `medium` | 60 分钟 | 推送 | 后勤/属地管理员 |
| `low` / `info` | 24 小时 | 无 | 信息流 |

> **为什么必须有时限**：没有时限的预警系统 = 一个通知列表。
> 有时限 + 有升级，才是**闭环的管理系统**。这也直接对应「功能完整性 20 分」。

预案不是一段文字，而是**一组具体动作**：


## 5. 路线 C · 天气预报应急联动（暴雨 / 冰雹 / 高温）

### 5.1 ★ 硬约束：必须走后端代理

**这条没有讨论余地。** 项目已经发生过一次 API Key 泄露事故（见 `五项规划...评估.md` §四.3），
而天气 API 恰恰是最容易被顺手写在前端的一类。

```
✅ 正确形态：前端 → 自家后端 /api/weather → 第三方天气 API（Key 只在服务端环境变量）
❌ 错误形态：前端 fetch('https://api.qweather.com/...?key=sk-xxxx')
```

⚠️ **动手前先确认**：泄漏的那把 Key **吊销了吗**？如果没吊销，先吊销。

### 5.2 数据源策略：三级降级（保证演示永不空场）

| 级别 | 数据源 | 成本 | 用途 |
| --- | --- | --- | --- |
| **L1 首选** | 天气 API（和风/中国天气网/OpenWeather）→ 后端代理 + **10 分钟服务端缓存** | Key + 一个小服务 | 真实数据，说服力最强 |
| **L2 降级** | **服务端定时抓取**（每 30 min 一次）→ 落成静态 JSON → 前端只读 | **零 Key、零实时依赖** | ★ 演示最稳；数据仍是真实的，只是延迟 ≤30 min |
| **L3 兜底** | 预置场景 JSON（暴雨红警 / 冰雹橙警 / 高温橙警各一份） | 零 | **演示脚本可控**——现场演示必须能"演"出想要的天气，不能等天下雨 |

> ★ **强烈建议 L2 + L3 组合，不急于上 L1**。理由：
> ① 校园安全预警对**分钟级延迟不敏感**（气象预警本身就是小时级的）；
> ② 演示现场网络不可控，L2 的静态 JSON **永不失败**；
> ③ 省掉一个后端服务的部署与运维，**把时间留给路线 D 的联动**。
> 在方案书里写清「L1 已预留接口，演示采用 L2 快照」，**这本身就是架构能力的证明**。

### 5.3 适配器（照抄 `httpCampusDataSource.js` 的模式）

```js
// src/data/weatherDataSource.js
export function createWeatherSource({ mode = 'snapshot' }) {
  const impl = {
    snapshot: snapshotSource,   // 静态 JSON（L2/L3）
    live: httpWeatherSource,    // /api/weather 代理（L1）
  }[mode]
  return { getCurrent: () => impl.current(), getAlerts: () => impl.alerts(),
           subscribe: (fn) => impl.on(fn) }
}
```

**禁止在组件里直接 `fetch`** —— 与 `httpCampusDataSource.js` 保持同一种形态，
这是「方案完整性 20 分」里"架构一致"的体现。

### 5.4 ★ 核心设计：从「气象级别」翻译成「校园处置动作」

**直接透传气象台的预警级别是没用的**（"暴雨橙色预警"对校园管理者不构成任何行动指令）。
价值在于**映射表**：

| 气象预警 | 校园风险点 | 自动处置动作 | 涉及现有零件 |
| --- | --- | --- | --- |
| **暴雨 蓝/黄** | 低洼路段积水 | 该路段标记湿滑 + 代价 ×1.35 | ★ `edgeCost()` 的 `RAIN` 模式**已有** |
| **暴雨 橙/红** | 地下车库倒灌、下沉广场 | ① 低洼边置入 `blocked_edges` ② 车库入口封闭 ③ 户外活动暂停 ④ **高亮环廊避雨通道** | ★ `buildGraph(blockedSet)` + `ROUTE_MODES.RAIN` 均已存在 |
| **冰雹** | 教学楼门厅、自行车棚、露天球场 | ① 推送「就近避险点」② 露天球场标记关闭 ③ 校园广播模板 | `HOTSPOT_TYPES.CLOSURE` 已有 |
| **高温 橙/红** | 体测/军训/户外课程、中暑风险 | ① 关联体育课与军训时段 ② 推送补水点与阴凉路线 ③ 户外活动建议调整 | `ROUTE_MODES` 可加 `SHADE` 模式 |
| **大风 黄+** | 树木倒伏、临时围挡 | ① 行道树密集路段提示 ② 临建围挡核查任务派单 | 派单机制（路线 B 顺带产出） |
| **雷电** | 空旷场地、水域 | 操场/湖边挑台临时关闭 | `HOTSPOT_STATUS.CLOSED` 已有 |

> ★ **这张表是整个路线 C 的价值所在**。它证明的不是"我们接了天气 API"（谁都能接），
> 而是「**我们把气象数据翻译成了校园可执行的处置动作**」。
> 同样一条「暴雨红色预警」，别的产品弹一个红框，你的产品**关掉车库、改了路线、派了单**。

### 5.5 预警等级变化 → 自动生成待办

```
气象等级升档（黄→橙）→ 自动创建预警卡片 + 关联预案（PLAYBOOK.weather_*）
                     → 推送对应责任人（走路线 B 的 SLA 时限）
气象等级降档/解除    → 自动解除封路 → 路线恢复 → 归档（形成"本次天气事件处置记录"）
```

★ **归档本身就是资产**：期末可以统计「本学期因暴雨封路 7 次、累计影响 3200 人次」——
这是**从功能到数据资产的跃迁**，对应「总结展望 5 分」。

**成本**：2 天（含代理或静态快照 + 映射表 + 联动）｜ **前置**：确认 API Key 已吊销

## 6. 路线 D · ★ 安全 ↔ 路网双向联动（核心亮点）

### 6.1 为什么这条是亮点

市面上 90% 的校园安全系统，**预警和导航是两个不相干的模块**：
预警面板响了，用户还得自己去查路线。**联动把两个模块变成一个动作。**

而这个项目**恰好具备别人没有的条件**：路网、A*、动态封路、避雨/夜安四种模式、
路线对比渲染（`RouteBand + RouteCore + RouteFlow`）**全都已经写好了**。
⇒ 联动的**边际成本极低，但是演示效果和评分权重极高（创新性 20 分）**。

> 一句话总结这条的价值：**把已有零件重新接线，就能得到别人要重写一遍才能有的能力。**

### 6.2 双向闭环机制

```
        ┌──────────────────────────────────────────────┐
        │                                              │
   预警发布                                         预警解除
        │                                              │
        ▼                                              ▲
  blocked_edges += 危险边                          证据矛盾 / 已处置
  edgeCost ×= 风险系数                                  │
        │                                              │
        ▼                                              │
   A* 重算（aStar() 一行不改）───────────────────────────┘
        │
        ▼
   路线对比渲染：原路线（灰虚线）+ 新路线（高亮 + 流动粒子）
   + 一句 AI 说明：「原路线经三食堂东侧，该路段被占用，已改走 XX，多 120 m / 约 2 分钟」
```

**★ 实现要点（§6 已定，照做）**：**不改 `aStar()`，改图的构建**。
`buildGraph()` → `buildGraph(blockedSet)`。封路与解封是**同一套机制的两个方向**，不是两个功能。

### 6.3 三种联动形态（从简到繁，可逐级实现）

| 形态 | 机制 | 演示效果 | 成本 |
| --- | --- | --- | --- |
| **① 危险区规避** | 预警地点 → 半径 R 内的边代价 × 系数 | 路线自然绕开 | 0.5 天 |
| **② 硬封路** | 预警地点 → 边置入 `blocked_edges` | 路线强制改道 + 距离变化可见 | 0.5 天 |
| **③ 应急疏散/救援路径** | 反向寻路：从危险点 → 最近安全出口/集结点 | ★ 疏散动画 + 多路径同时渲染 | 1 天 |

**★ 形态 ③ 是"安全"独有的能力** —— 普通导航只做「我怎么去」，安全管理还要做
「**大家怎么撤**」。这是把产品从"导航工具"提升为"安全系统"的关键动作。

```
疏散模式：
  ① 各建筑门口节点 → 最近安全集结点（多源最短路，aStar 跑 N 次，N ≤ 30，成本可接受）
  ② 每条疏散路线按人流量分配宽度（避免全挤一条路 —— 这正是路线 A 的"空间传导"派上用场）
  ③ 3D 视图下渲染人流动线 + 集结点标注
```

### 6.4 与路线 A/C 的接线点（复用而非新建）

| 上游 | 输出 | 喂给谁 |
| --- | --- | --- |
| 路线 A 人流超限 | 路段 `congestion` 系数 | `edgeCost()` 的同一套系数 —— **交通热力图与风控共用** |
| 路线 C 暴雨预警 | 低洼边集合 | `buildGraph(blockedSet)` —— **与封路同一套机制** |
| 路线 C 避雨需求 | `ROUTE_MODES.RAIN`（**已存在**） | 直接切换模式即可，**零新增代码** |
| 路线 B 事件发布 | 事件类型 + 地点 | 触发封路/解封 |

> ★ 这张表说明**四条路线不是四件事，是一件事的四个侧面**。
> 在方案书里用这张表，能直接证明「方案完整性」。

**成本**：2 天 ｜ **前置**：**必须修路网缺陷 2**（中轴↔南段外环无连接边）——
不修的话「封路后距离不变」，**联动演示会当场失败**

### 7.3 AI 安全简报（LLM 增强 · 0.5 天）

把结构化数据交给 LLM 生成自然语言简报，**这是"AI 融合深度"的可见落点**：

```
输入：{ 预警列表, 人流序列, 天气快照, 处置记录, 历史同期 }
输出：「今日 14:00–16:00 第三食堂将迎高峰（预测 352 人 / 容量 400，叠加暴雨橙色预警，

★ 关键：LLM 只做"表达层"，不做"判定层" —— 级别、阈值、处置动作全部由规则引擎产出。
  ⇒ 可解释、可审计、不会胡说。这条边界必须写进方案书。
```

**成本**：4–5 天（P1 预测 + 大屏 + 简报）

## 11. 方案书可用的三句"亮点话术"

答辩时反复讲这三句，比讲一百个功能有效：

1. **「预警和导航在我们的系统里是同一个动作。」**
   —— 预警发布 → 封路 → 重算 → 路线对比渲染，一句话说完双向联动。

2. **「我们的 AI 会承认自己不确定。」**
   —— 安全类事件可信度不足时不打点、不自动发布，进人工队列，
   而且**每一分都能打印出来**（base +40% / 官方源 +35% / 群体佐证 +18% / …）。这是 AI 可解释性的正面示范。

3. **「我们不预报天气，我们把天气翻译成行动。」**
   —— 暴雨红警 → 关车库 + 封低洼 + 改路线 + 派单 + 归档。气象数据谁都能接，翻译能力才是产品。
