# 校园数字孪生服务平台：新版产品与技术总方案

> 状态：新版主方案（2026-09-26）
>
> 本文替代 `2026-09-21-model-anchored-labels-and-routes-design.md` 对后续开发的指导作用。旧文档保留作模型锚点和路线实现的历史记录，不再作为总体产品规划依据。

## 1. 这次重新整理后的结论

项目不再定义为“一个带 3D 模型的校园地图”，而定义为：

> **以 3D 校园地图为主界面，把地点、路线、校园动态和管理操作统一到同一套空间数据上的校园数字孪生服务平台。**

地图始终是页面的主视觉和主操作区；搜索、地点详情、路线、图层、我的位置、角色、设置和管理发布等小功能放进可收起的侧边或底部面板。这样既符合现在的界面方向，也能让后续功能围绕同一个核心扩展，而不是不断往页面上堆新的卡片。

项目的第一条完整闭环是：

```text
找地点 → 看地点状态/校园动态 → 选择路线 → 路线受施工或关闭状态影响 → 管理员发布/修改状态 → 地图与路线同步变化
```

以后再接入学生上报、AI 结构化、事件去重、可信度聚合和生活服务，但这些功能都必须落在已有的地点锚点、路线边和状态模型上。

## 2. 已确认的项目边界

### 2.1 当前已有基础

- React + Vite + Three.js + GLB 模型。
- 地点、事件、路线和角色已有本地数据结构。
- 模型中已经有 `ANCHOR_*` 位置锚点，地点标签和路线可以绑定到模型坐标。
- 已有访客、学生、管理员三种演示角色。
- 已有模拟我的位置、第一人称模式、管理员发布热点的雏形。
- 本地数据源已经为未来替换成真实接口留下了入口。

### 2.2 当前不做的事情

- 不重新建模，不把地图构建工作重新放回本项目。
- 不立即迁移到 React Three Fiber；当前 raw Three.js 方案已经能加载 GLB，先保持稳定。
- 不把真实 GPS、室内定位、碰撞检测、复杂登录权限作为比赛版前置条件。
- 不让 AI 直接控制地图或直接生成不受约束的 JSON。
- 不把尚未稳定的 3D 新标准、WebGPU 或生成式 3D 作为关键路径。

## 3. 产品结构：一张地图、三条闭环、四种状态

### 3.1 一张地图

3D 地图是唯一的主工作区：

- 建筑、校门、道路、服务点使用模型锚点和路线图坐标。
- 地点状态、热点、活动、施工和路线均以地图覆盖层表达。
- 侧边功能打开时地图仍保持可见，不跳到独立后台页面。
- 移动端可以把侧边栏改成底部抽屉，但不改变数据和交互模型。

### 3.2 三条闭环

#### A. 校园基础闭环

```text
GLB 模型 → Anchor 注册表 → 地点/服务点 → 道路图 → 路线结果
```

这是所有功能的空间基础。没有可靠的 `locationId`、`anchorId`、`entryNodeId`，事件和路线都会断链。

#### B. 校园动态闭环

```text
管理员发布（首版）/用户上报（以后）
→ 结构化事件
→ 地点锚点匹配
→ 去重与可信度
→ 待核实/已确认/已关闭
→ 地图热点、地点状态、路线约束
```

首版优先做管理员发布，表单直接产生结构化事件；未来接入自然语言上报时，只替换“事件输入适配器”，不改变地图、审核和路线消费方。

#### C. 校园服务闭环

```text
搜索地点/服务 → 查看开放状态和动态 → 选择路线模式 → 查看分步提示 → 到达
```

校园服务包括图书馆、食堂、宿舍、教学楼、体育馆、医务室、快递点、打印点、充电点和无障碍设施。首版只需要覆盖已有核心地点，但数据结构必须支持继续增加点位。

### 3.3 四种状态

所有重要对象都要有明确状态，而不是只有颜色：

- 地点状态：开放、临时关闭、维护中、未知。
- 事件状态：草稿、待核实、已确认、已驳回、已过期、已关闭。
- 路线状态：可用、绕行、不可达、数据待更新。
- 数据源状态：本地演示、同步中、同步失败、最后更新时间。

## 4. 页面与基础功能规划

### 4.1 页面骨架

```text
┌────────────────────────────────────────────────────┐
│ 品牌 / 校园名称     数据源状态        角色 / 头像   │
├────────────────────────────────────────────────────┤
│ 搜索框、地点分类、热点提示                           │
│                                                    │
│             3D 校园地图主视区                       │
│  可收起工具侧栏                              指南针 │
│                                                    │
│        地点详情 / 路线预览 / 状态提示抽屉            │
└────────────────────────────────────────────────────┘
```

### 4.2 地图侧栏的基础功能

侧栏第一版就要规划完整，但可以分批实现：

1. 地点分类：教学、生活、住宿、运动、服务、出入口、无障碍。
2. 图层：地点标签、热点、活动、道路、路线、我的位置、施工区域。
3. 视图：重置视角、俯视/第一人称、夜间模式、低性能模式。
4. 我的位​​置：首版用校园地点模拟，未来替换定位服务。
5. 角色模式：访客、学生、管理员；首版是演示切换，后续接真实权限。
6. 设置：主题、动画、标签密度、地图质量、单位、数据刷新、恢复演示数据。
7. 管理发布：管理员新增/修改/关闭校园动态，选择地点和影响道路。

每个侧栏工具都应该有关闭、空状态、错误状态和键盘可达行为，不能只实现“点开后展示一段说明文字”。

### 4.3 地点详情

地点详情卡统一显示：

- 名称、分类、楼层或入口。
- 开放状态、开放时间、当前人流。
- 当前热点和活动。
- 服务能力，例如预约、打印、快递、充电、无障碍。
- 数据来源和更新时间。
- `到这里去`、`从这里出发`、`收藏`、`分享/复制链接`等操作。

详情卡不要自己维护一份状态；它只消费地点领域对象和事件投影，避免地图、详情、路线面板出现不一致。

### 4.4 路线功能

首版路线模式保留：最短、无障碍、避开施工、避雨、夜间安全。

每个路线结果必须说明：

- 起点和终点。
- 路线距离、预计用时、模式。
- 当前是否绕行，绕开的原因是什么。
- 受影响的事件或施工信息。
- 路线不可用时的原因和可选替代模式。

路线图使用模型坐标中的节点和边。事件不能只在地图上显示橙色点，还要通过 `affectedEdgeIds` 或 `blocked` 属性影响路径计算。

### 4.5 设置与软件基础设施

设置不是最后才补的装饰功能，应在应用壳子阶段建立统一入口：

- 外观：浅色、深色、夜间地图。
- 地图：标签显示密度、热点显示、路线动画、阴影质量。
- 导航：默认路线模式、默认起点、步行速度。
- 数据：本地演示数据/接口数据、刷新间隔、清空缓存、恢复初始数据。
- 无障碍：减少动画、高对比度、键盘焦点、文字提示优先。
- 演示：一键恢复比赛演示状态、显示版本号和数据源。

所有设置统一写入 `localStorage`，但通过 `settingsRepository` 访问。组件不得直接读写 `localStorage`，未来接账号配置时只替换仓库实现。

### 4.6 P0 软件基础底座

以下能力比夜景、天气、第一人称更基础，列为第一批必须补齐的功能。

#### 设置面板

设置面板按功能分组，而不是一张越来越长的表单：

- 地图显示：日间/夜间、建筑标签、热点、路线、当前位置、状态颜色。
- 地图操作：重置视角、全屏、鼠标灵敏度、默认视图、自动旋转、操作提示。
- 导航偏好：默认路线模式、是否优先遮雨、是否默认避开施工。
- 数据与演示：保存当前演示状态、恢复默认数据、清空路线、清空模拟位置、更新时间、模型版本。
- 关于系统：软件版本、地图版本、数据来源、快捷键和使用说明。

#### 持久化与状态分组

当前内存 `useReducer` 状态按四个语义组整理：

```text
settings  地图显示、导航偏好、性能和演示设置
session   当前角色、模拟位置、选中地点、最近路线、收藏
map       相机、侧栏、图层、第一人称和全屏状态
data      地点、事件、路线、加载/同步/错误状态
```

首版通过 `localStorage` 持久化设置、模拟位置、当前角色、管理员修改和最近路线。组件只调用 `storage` / repository，不直接读写浏览器存储；未来把 repository 替换成 API 或账号配置时不改 UI。

#### 通用地图控制

地图必须提供放大、缩小、重置视角、聚焦当前地点、聚焦当前位置、全屏、图例和距离/比例信息。操作入口可以收在侧栏，但不能只依赖 Three.js 默认鼠标行为。

#### 搜索基础

搜索统一面向可检索资源，而不是只匹配建筑名：

```text
地点 / 别名 / 拼音关键词 / 服务 / 活动 / 通知 / 快捷操作
```

必须有无结果状态，后续再加最近搜索、常用地点收藏和模糊匹配。地点别名、服务标签和活动标题都进入同一个搜索索引接口。

#### 导航基础体验

路线面板除折线外必须支持起点和终点互换、清空、距离、预计时间、分段指引、已避开施工、无障碍说明、聚焦路线、重新规划和不可达原因。路线结果要回答“为什么这样走”，不能只显示一条线。

#### 统一反馈

统一处理 GLB 加载中/失败、数据加载中/同步失败、无搜索结果、无可用路线、地点关闭、WebGL 不支持和浏览器能力不支持。基础组件包括 `Toast`、`LoadingState`、`EmptyState` 和 `ErrorState`。

#### 管理员可恢复操作

管理员修改必须支持编辑、保存、取消、撤销、恢复默认、修改时间、修改人和发布状态。首版可以只实现当前会话和本地存储的撤销栈，但数据结构要保留操作记录，避免误操作不可恢复。

#### 移动端基础交互

侧栏在窄屏变为抽屉，地点详情和路线面板变为底部弹窗；模型支持触摸旋转/缩放，按钮保持可触摸尺寸，重要操作不依赖悬停。第一人称虚拟摇杆属于后续阶段，但相机模式切换的接口现在就要留好。

## 5. 核心数据契约

### 5.1 地点与模型锚点

```js
{
  id: 'library',
  name: '图书馆',
  category: 'study',
  modelAnchorId: 'ANCHOR_Library',
  entryNodeId: 'library-entry',
  aliases: ['图书馆', '校图书馆'],
  openStatus: 'open',
  crowdStatus: 'normal',
  services: ['study', 'reservation'],
  source: 'local-demo',
  updatedAt: '2026-09-26T08:00:00+08:00'
}
```

锚点、入口节点和别名必须是独立字段。别名是未来“图书馆二楼”“去图书馆”这类自然语言定位的基础。

### 5.2 路线图

```js
{
  id: 'axis-library-to-library',
  from: 'axis-library',
  to: 'library-entry',
  distance: 54,
  accessible: true,
  covered: true,
  safeAtNight: true,
  blocked: false,
  blockedByEventIds: []
}
```

基础路线图是静态配置；施工、临时封路等动态变化通过 `blockedByEventIds` 关联事件，不直接修改原始地图资产。

### 5.3 事件对象

首版管理员表单也必须使用这个对象，不能单独设计一套“演示热点对象”：

```js
{
  id: 'event-library-001',
  type: 'closure',
  title: '图书馆临时关闭',
  rawText: '图书馆因设备检修临时关闭',
  locationId: 'library',
  anchorId: 'ANCHOR_Library',
  floor: null,
  affectedEdgeIds: ['axis-library-to-library'],
  severity: 'medium',
  startAt: '2026-09-26T12:00:00+08:00',
  endAt: '2026-09-26T18:00:00+08:00',
  sourceType: 'manager',
  sourceRefs: [],
  confidence: 1,
  trust: {
    verdict: 'verified',
    score: 1,
    reasons: ['管理员发布']
  },
  moderationStatus: 'verified',
  createdAt: '2026-09-26T11:30:00+08:00',
  updatedAt: '2026-09-26T11:30:00+08:00'
}
```

未来用户自然语言上报只需要先生成 `rawText`，再由结构化提取器填充地点、时间、类型和影响边。所有原始文本、来源和处理结果都要保留，便于解释和复核。

### 5.4 数据源接口

现有本地数据源继续使用，但接口要稳定成以下语义：

```js
loadSnapshot()
listLocations(filters)
listEvents(filters)
getRoute(request)
createEvent(input)
updateEvent(id, patch)
closeEvent(id)
getSettings()
saveSettings(patch)
resetDemoData()
```

本地实现使用静态 JSON + `localStorage`；未来 HTTP 实现可以映射到 `/api/locations`、`/api/events`、`/api/routes`、`/api/settings`，组件层不改调用方式。

## 6. 动态事件和 AI 能力的落地顺序

### 6.1 首版：管理员发布优先

管理员填写地点、类型、标题、时间、严重程度、影响道路后发布。发布流程：

```text
草稿 → 预览影响地点/道路 → 发布 → 地图热点与地点状态更新 → 路线重新计算 → 关闭/过期
```

首版管理员发布就能展示数字孪生的核心价值，不依赖真实用户量和外部接口。

### 6.2 下一版：受约束的事件结构化

根据调研文档，未来自然语言事件处理必须是“先约束、后生成”：

1. 原文清洗和敏感内容预检。
2. 地点匹配：精确名称/别名 → 向量匹配 → 需要时人工确认；不允许模型凭空创建地点。
3. 受限枚举输出：事件类型、地点、楼层、时间、严重程度、证据类型、原文。
4. Schema 校验失败时进入待核实，不直接上图。
5. 结构化成功后再做时空语义去重。

### 6.3 去重和可信度

首版可以用可解释的规则基线：同一锚点或 150 米内、45 分钟内、事件类型一致且文本相似度达到阈值时归并为同一事件簇。阈值只作为可配置初始值，后续用标注样本校准。

可信度不使用黑箱 0–1 分数，而保留原因：

- 管理员官方发布。
- 多个独立上报相互印证。
- 校园官方资料检索到支持信息。
- 地点与事件语义一致。
- 信息过期、来源单一或定位不明确。

安全事件或低置信度事件必须显示“待核实”，必要时进入管理员复核，不自动改变关键路线。

### 6.4 后续 AI 方向

只有 P0 数据链路稳定后才考虑：

- 校园知识库/轻量 GraphRAG：回答“哪里办理、需要什么、截至何时”。
- 人流预测：先做历史均值和时间周期基线，再考虑 STGNN。
- 端侧小模型：分类、敏感内容筛查、离线兜底，不承担关键地点推断。
- 评测集：先人工标注约 200 条事件，测地点提取 F1、事件去重准确率、可信度排序和路线避障正确率。

暂不把生成式 3D、世界模型、动态 4D、复杂推荐大模型和 MCP/A2A 放到比赛版关键路径。

## 7. 技术取舍

### 7.1 继续使用当前 3D 方案

- 继续 Three.js + GLB + Draco。
- 使用模型锚点绑定标签和地点。
- 使用配置化路线图而不是从三角网格自动推导道路。
- 使用 `three-mesh-bvh` 或类似方案时先测量，再引入。
- 用 glTF-Transform 做模型检查和定向压缩；模型格式升级不作为当前关键路径。
- WebGPU、TSL、批量渲染等只在性能证据表明需要时启用，并保留 WebGL 降级。

### 7.2 借鉴开源项目的具体方式

以下只借鉴方法，不直接复制实现：

- NCUmap：Blender → GLB、模型锚点、建筑标签和性能优化思路。
- Campus Navigate 及 SHU campus navigation：A* / Dijkstra、路网边属性和路线步骤。
- MapMIT：校园事件发布、管理和历史数据的产品闭环。
- iitk：原始数据、清洗数据、构建索引、浏览器验证的分层方式。
- Campus-Navigate-3D-FE：前端与未来 API 的数据边界。
- CIC2026 Digital Twin Campus：实体/状态/可视化之间的数字孪生映射。

## 8. 建议的代码分层

```text
src/
├── app/                 应用状态、路由、reducer、selectors
├── domain/              地点、事件、路线、可信度、状态转换
├── data/                本地 JSON、仓库、storage、模型锚点、路线图
├── services/            local/http/AI 适配器，统一错误与加载状态
├── features/
│   ├── map/             3D 场景、锚点标签、图层、相机
│   ├── locations/       搜索、筛选、详情
│   ├── routes/          路线规划、步骤、模式切换
│   ├── events/          热点、管理员发布、审核状态
│   ├── roles/           访客/学生/管理员
│   ├── settings/        设置、演示恢复、数据源
│   └── feedback/        Toast、Loading、Empty、Error
└── shared/              格式化、日志、可访问性和通用控件
```

组件只调用 domain/service，不直接改路线图、不直接写 `localStorage`、不直接读取事件数组。这样后续文件变大时，替换数据源或增加页面不会牵动 3D 渲染核心。

## 9. 分阶段开发路线

### 阶段 0：定住契约和边界

- 固定地点、锚点、入口节点、路线边和事件 Schema。
- 将本地数据源与未来 API 接口写成同一组方法。
- 增加数据校验：重复 id、缺失锚点、缺失路线入口、非法事件状态。

### 阶段 1：P0 软件基础底座

1. 设置面板真实可用，覆盖地图显示、地图操作、导航偏好、数据演示和系统信息。
2. 设置写入 `localStorage`，支持恢复默认设置。
3. 将状态按 `settings/session/map/data` 分组，并通过 selectors 供组件读取。
4. 增加地图放大、缩小、重置视角、聚焦、全屏、图例和距离信息。
5. 增加 `Toast`、`LoadingState`、`EmptyState`、`ErrorState`，覆盖模型、数据、搜索和路线状态。
6. 完善搜索的地点/别名/服务/活动接口和无结果状态。
7. 为管理员修改加入本地持久化、取消、撤销和恢复默认。
8. 适配窄屏侧栏抽屉、详情底部弹窗和触摸地图操作。

第一阶段完成前，不扩展天气、复杂夜景、人流预测或 AI 抽取。

### 阶段 2：P0 导航基础体验

- 6 个核心地点全部绑定模型锚点。
- 路线使用模型坐标和 A*。
- 支持起点/终点互换、清空、聚焦路线和重新规划。
- 路线面板显示原因、距离、时间、分段指引、无障碍和施工绕行说明。
- 施工、关闭状态影响路线，不可达时显示原因。

### 阶段 3：管理员动态闭环

- 管理员发布、编辑、关闭、过期事件。
- 事件绑定地点、锚点和影响道路。
- 地图热点、地点状态和路线实时联动。
- 加入操作记录和数据更新时间。

### 阶段 4：可信事件能力

- 接入事件 Schema 校验、别名匹配、规则去重和可信度解释。
- 增加待核实状态和审核入口。
- 保留原始文本与证据，支持“为什么这样判断”。

### 阶段 5：服务扩展和比赛包装

- 学生常用服务、收藏、活动、打印/快递/充电/医务室。
- 人流热度基础统计和历史趋势。
- 一键演示、架构图、数据流图、评测指标和项目文档。

## 10. 比赛演示主流程

```text
1. 访客模式进入，地图作为主界面
2. 搜索“图书馆”，点击模型上的图书馆标签
3. 查看开放状态、热点和活动
4. 选择“避雨路线”，路线显示在真实模型道路上
5. 切换管理员模式，发布“图书馆东侧道路施工”
6. 事件显示为已确认/待核实，并标记受影响道路
7. 返回访客模式，地图显示施工热点，路线自动绕行
8. 选择学生模式，搜索打印、快递或充电服务
9. 打开设置切换夜间/低性能模式，刷新后设置仍保留
10. 选择模拟我的位置并进入第一人称，完成从当前位置到目标点的演示
```

这条流程可以同时证明：3D 场景、空间锚点、搜索、路线算法、动态状态、管理员发布、角色切换、数据持久化和未来扩展边界。

## 11. 新版验收标准

1. 地图仍然是主要展示区，侧栏可收起且不会破坏地图操作。
2. 地点、热点、路线和我的位置使用同一套模型锚点/路线节点体系。
3. 设置面板、状态持久化、恢复默认、图层控制、地图控制和快捷键说明可用。
4. 加载、错误、空状态和 Toast 覆盖模型、数据、搜索和路线主要分支。
5. 起终点互换、清空、聚焦、重新规划、分段指引和不可达原因可用。
6. 管理员修改支持保存、取消、撤销、恢复默认和时间/修改人记录。
7. 管理员发布事件后，地图、地点状态和路线至少有一项可观察变化；施工事件必须能影响路线。
8. 事件保留来源、原文、状态、时间和影响道路，不能只保留一个颜色或标题。
9. 本地实现与未来真实接口使用相同的数据语义，组件不依赖具体 API 字段。
10. AI 相关能力即使关闭，管理员发布、地图展示和路线规划仍能独立运行。
11. 窄屏侧栏、详情和路线面板可用，重要操作不依赖鼠标悬停。
12. `npm test -- --run`、`npm run build` 和浏览器主流程验收均通过后，才进入下一阶段。

## 12. 最终原则

**先把“地图 + 地点 + 路线 + 管理员状态变化 + 软件基础设置”做成稳定软件，再把 AI、真实接口和预测能力接到已经稳定的数据闭环上。**

地图负责让信息有空间位置，事件负责让数字孪生发生变化，路线负责把变化转成可执行行动；三者才是这个项目的核心。
