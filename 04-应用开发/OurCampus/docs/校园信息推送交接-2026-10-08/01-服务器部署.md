# 服务器部署顺序

## 1. 核对已有库

项目根地址：`https://hkdblizadnkskxslyjyq.supabase.co`。数据库 REST 地址才带 `/rest/v1`；Supabase CLI 和前端 SDK 使用根地址。

用 SQL Editor 执行 `database/00-preflight.sql`。若提示缺表或字段，先对照 `reference/01-CampusTwin-schema.sql` 与当前真实结构，由项目管理员补差异。基础脚本含直接 CREATE TABLE 和建桶语句，只用于全新业务库，已有库不要重跑，也不要为了匹配脚本清空数据。

检查通过后执行 09 号增量 SQL。其事务失败会回滚，不应只挑部分语句执行。新建 `campus_reports`、`campus_subscriptions`、`campus_push_devices`、`campus_push_receipts` 与私有 `information_jobs`；复用 `notifications` 和 `campus_events`。

## 2. 配置服务器 Secrets

包内模板 `server-secrets.example.env` 的值为空。可直接在 Dashboard → Edge Functions → Secrets 填写，或使用已登录的 Supabase CLI。不要把填好的 env 文件放进共享仓库。

| Secret | 值 |
| --- | --- |
| `AUV_BASE_URL` | AI 同学提供的 HTTPS 服务根地址，不带 `/docs`、`/v1` 或 `/v1/chat/completions` |
| `AUV_API_KEY` | 模型网关授权密钥 |
| `CAMPUS_WORKER_TOKEN` | 独立随机令牌，至少 32 字符，不复用任何客户端 key |
| `GETUI_APP_ID` | 个推应用 AppID |
| `GETUI_APP_KEY` | 同一应用 AppKey |
| `GETUI_MASTER_SECRET` | 同一应用 MasterSecret，仅服务器保存 |

`SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY` 和 `SUPABASE_ANON_KEY` 由 Supabase 托管函数环境提供，不能放到 `VITE_` 配置或 APK。工作函数使用 service_role；`auv-assistant` 仍验证用户登录，按用户权限读取校园上下文。

生成独立工作令牌（只在部署者本机运行，不粘贴输出到共享文档）：

```powershell
node -e "process.stdout.write(require('crypto').randomBytes(32).toString('hex'))"
```

## 3. 部署函数

在解压后的根目录，或合并到已有部署工程后运行：

```powershell
supabase login
supabase functions deploy campus-information-worker --project-ref hkdblizadnkskxslyjyq
```

需要一并更新校园助手时再执行：

```powershell
supabase functions deploy auv-assistant --project-ref hkdblizadnkskxslyjyq
```

配置中 `campus-information-worker.verify_jwt=false` 让定时器使用独立工作令牌；函数内部严格验证 `x-campus-worker-token`，不是公开匿名分析接口。`auv-assistant.verify_jwt=true` 保持用户入口的鉴权。

## 4. Vault 与调度

在 Supabase Vault 界面新增两个命名 Secret：

| Vault 名称 | 值 |
| --- | --- |
| `campus_worker_url` | `https://hkdblizadnkskxslyjyq.supabase.co/functions/v1/campus-information-worker` |
| `campus_worker_token` | 与 Edge Functions `CAMPUS_WORKER_TOKEN` 完全相同 |

若已存在同名条目，更新现有条目。不要创建多个同名值，不要输出 `vault.decrypted_secrets` 全表。

在 Dashboard 检查 Vault 可用、开启 pg_net 与 pg_cron，然后执行 10 号 SQL。SQL 创建名为 `campus-information-worker` 的每分钟补偿任务，任务正文不含明文密钥；队列入库时通过 pg_net 异步唤醒，工作函数完成一批后继续唤醒下一批。平台网络或排队会影响延迟，不承诺固定秒数。

10 号脚本会限制普通业务角色读取 pg_net 内部请求 / 响应表，避免读取包含工作令牌的请求头。如当前项目另有普通角色直接读取这些表的功能，先与原维护者协调。托管数据库和 service_role 的能力保留。

## 5. 管理员角色

在 Authentication 用户列表查到指定管理员的 UUID，在 SQL Editor 替换占位符后执行：

```sql
insert into campus_private.user_roles(user_id,role)
values ('替换为真实用户UUID'::uuid,'manager')
on conflict(user_id) do update set role='manager';
```

普通注册默认 student。客户端没有自助提权入口。管理员刷新账号资料后，消息中心会出现“审核”；审核标题、地点、内容、有效时间并勾选确认才能发布。

## 6. 启用顺序和边界

- 没有个推账号时可先完成 AI 和站内通知。缺少推送 Secret 的任务会重试最多五次后失败，站内通知不会丢失；补齐后按故障处理文档重排仍有效的失败任务。
- 公共通知发给确认发布时已有的全体注册用户；本版不自动给以后新注册的账号补发历史通知。
- 邮件注册 / 密码重置继续使用已有 SMTP 和验证码模板，本次不改认证配置。
- 确认过的官方事件不会因为一个上报者撤回线索就自动删除；管理员需确认结束。
- 失物照片、收藏、课表和附近设施的本机数据不在本次迁移范围。餐厅新评价另见 05 号说明，原有本机评价不自动迁移。不得把本机数据说成已同步到服务器。
