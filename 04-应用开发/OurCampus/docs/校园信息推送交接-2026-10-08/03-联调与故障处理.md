# 部署后联调与故障处理

当前交付已进行网页生产构建、Java 编译及 APK 签名检查；未代队友执行线上 SQL、部署 Edge Function、注册测试用户或完成真机推送。下面由拥有项目权限的队友在配置后检查。

## 联调顺序

1. 两个真实账号登录各自设备。甲发大厅聊天，乙能实时看到；普通聊天不会在 `campus_reports` 产生记录。
2. 甲主动“提交为动态”，或发布施工信息。`campus_reports` 入库，私有队列创建 analysis 任务；后台分析后保存摘要、状态和候选关联。
3. 普通账号看不到其他人的待审核施工信息，不能审核或给自己设置 manager。
4. 管理员核对施工地点、内容、结束时间，勾选确认并发布。产生一个真实 `campus_events` 事件，且每个当时已有注册账号各有一条通知，不受个人订阅限制。
5. 乙的消息中心出现未读通知，地图和热点展示审核后的事件；点开进入地点详情并能导航。已读统计随服务器记录更新。
6. 发布普通通知时选订阅范围，匹配地点 / 类别的账号收到；无匹配订阅的账号不收到。施工、封路和停水停电即使选订阅仍强制全员。
7. 同地点、近期寻物 / 招领且描述匹配时，两位作者收到“可能匹配”提醒；不应声称已经认领成功。撤回或完成后不再匹配。原始联系方式字段不进 AI 请求。
8. 手机上同意推送，取得 CID 并登记；另一个账号审核公共通知。在前台、后台和锁屏观察通知栏，点击应进入该账号的对应消息。厂商通道未配置时不能据基本通道检查宣称稳定后台推送。
9. 当前设备退出账号，旧账号设备绑定 enabled=false；换账号后重新允许 / 绑定。没有网络时软件先关闭本地推送，解绑失败会提示，恢复网络后重新执行退出，避免服务器继续保留旧绑定。
10. 网络中断后重复提交同一草稿、worker 并发领取、函数超时后补偿，不应创建重复报告或重复站内通知。提供者稳定 request_id 与设备受理回执尽量避免重复系统通知，但不承诺跨平台严格 exactly-once。

## 状态查询（SQL Editor，管理员执行）

```sql
select kind,status,count(*) from campus_private.information_jobs group by kind,status order by kind,status;
select kind,last_error,attempts,count(*) from campus_private.information_jobs where status in ('retry','failed') group by kind,last_error,attempts;
select jobname,schedule,active from cron.job where jobname='campus-information-worker';
select name from vault.secrets where name in ('campus_worker_url','campus_worker_token');
select public.campus_wake_information_worker(true);
```

只查看名称和统计，不把 Vault 解密值、service_role 或推送密钥截图发群。队列收到 wake 的 ID 表示 pg_net 入队，仍需看 Edge Function 日志 / pg_net 响应状态与业务结果。

## 常见情况

| 表现 | 检查 |
| --- | --- |
| App 提示 09 号服务尚未部署 | 确认 SQL 执行成功、前置表一致、函数 schema cache 刷新 |
| 任务长期 ready | 10 号脚本、Vault 名称、URL、cron active、pg_net / Edge Functions 配额 |
| worker 返回 401 | Vault 令牌与 `CAMPUS_WORKER_TOKEN` 不一致或长度不足 |
| `ai_unconfigured` / 分析失败 | AI HTTPS 根地址、AUV_API_KEY、模型 persona / extract 可用性；不要在日志中打印 key |
| `push_unconfigured` | 个推三个 Secret 尚未填写 |
| `push_auth_failed` | AppID / AppKey / MasterSecret 是否属于同一应用、平台授权是否有效 |
| `push_provider_rejected` / `push_not_accepted` | 个推控制台请求限制、CID、渠道配置、返回码；站内通知仍保留 |
| 消息中心更新但通知栏没有 | 本设备权限 / CID / enabled、厂商通道、系统省电或强制停止、通知是否已读或事件过期 |
| 推送点击提示不属于账号 | 检查当前登录账号，服务器不会绕过 recipient_id 权限读取别人的消息 |
| 事件结束后还在历史消息 | 历史通知保留是预期；地图当前热点应退出，旧系统提醒不会补发 |

## 配置补齐后恢复队列

分析失败：作者在“我的上报”点重试，或管理员核对任务后重新排队。公共通知仍需要人工审核。

个推配置补齐后，用 SQL Editor 对失败 / 重试的未读通知任务重排。工作函数会再次检查目标是否有效、是否已读，已受理设备不再重复发送。

```sql
update campus_private.information_jobs j
set status='ready',attempts=0,available_at=now(),lease_until=null,claim_token=null,last_error=null
where j.kind='push' and j.status in ('failed','retry')
  and exists(select 1 from public.notifications n where n.id=j.target_id and n.read_at is null);
select public.campus_wake_information_worker(true);
```

不要重排 done / cancelled，也不要删除 `campus_push_receipts` 来强制重发。没有启用通知的设备会正常跳过；以后启用只从后续通知接收，历史通知可在消息中心查看。

## 暂停后台

管理员可在 Cron 控制台暂停补偿任务，并停用队列 wake trigger；现有消息、账号、聊天保留。不要删除业务表或执行基础建库脚本。重新开启后再唤醒待处理任务。退出账号、关闭通知与解除订阅应能独立工作。
