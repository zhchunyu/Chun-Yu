# 实时输入接入设计 · v1.0

> 面向 C 端的未来校园社区软件 —— 演示期（虚量数据）如何接入并处理真实用户实时输入
> 定稿 2026-09-26 ｜ 部署形态：**C 方案（公网只读 + 现场可交互）**
> 用途：`06-竞赛材料` 方案书「技术实现 20 分 / 方案完整性 20 分」的正文素材源

---

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| 演示用虚量数据，真实输入怎么接？ | **数据源可插拔**：`EventSource` 三实现（Mock / Manual / Real），上层管线不知道数据从哪来 |
| 真实输入以什么形式呈现？ | 三层分离：**输入层**（地图选点 + 一句话）／**处理中**（5 步可见）／**呈现层**（分级打点 + 聚合计数） |
| 卡车挡路怎么定位并重算路线？ | 地点字段**约束为 ANCHOR 枚举** → 锚点匹配 → 吸附最近路段 → 路段置为不可通行 → A\* 重算 |
| 怎么发现"某条路长期无人经过"？ | 位置 ping 吸附到**路段**做时间桶计数 → 与**同时段中位数**基线比 → 排除已知原因 → 产出「建议核查」任务 |
| 演示期怎么落地？ | **一套代码 + `?mode=` 开关**：公网 `readonly`（只读 + 自动巡航），现场 `interactive`（评审可上手） |

**三条硬判断**

1. **不做真值定位** —— 需求基线 §五 已定「虚拟位置，不做真实定位追踪」；且真实坐标无法映射到虚构的山河大学。
2. **"自动定位"= 自动带出位置 + 位置随移动更新**，不是 GPS。手动选点是**覆盖**（override），不是另一套模式。
3. **演示期只能演示"机制"不能演示"效果"** —— 通行热度异常检测依赖历史基线，我们没有真实历史数据 ⇒ 合成 7 天通行日志再注入异常。

## 1. 部署形态：C 方案

评审有两个使用场景，用**同一套代码、两个模式**同时满足：

| | 公网 track | 现场 track |
| --- | --- | --- |
| 入口 | `site/preview.html`（部署在 `workbuddy_sites_deploy`） | `web-demo/index.html`（本机） |
| 模式 | `?mode=readonly`（默认） | `?mode=interactive` |
| 能做什么 | 看 3D 全园、自动巡航蓝点、预置事件回放、只读信息流、AI 问路 | 全部 + **评审自己选点上报** + 手动覆盖定位 |
| 上报入口 | 隐藏 | 显示 |
| 价值 | 评审随时点开链接即可验证 | 评审能上手玩，说服力最强 |

**为什么几乎零成本**：`preview.js` 已有 `const Q = new URLSearchParams(location.search)` + `qs()` 助手，
`app.js` 已有 `new URLSearchParams(location.search)` + `q.get()`。加模式开关只是多一个 `qs('mode','readonly')`。

**共享模块**：`location.js` 与 `events.js` 从 `web-demo/src/` 提升为两个页面共用的模块。

> ★ 构建约束：`tools/make_site.py` 的 `SRC_FILES = ('preview.js', 'navigation.campus.js')`，
> 且脚本会把**不在白名单里的 `.js` 当孤儿清掉**。新增共享模块必须同步改这个白名单，否则构建后被删、线上 404，
> 而 ES module 的 404 会让**整个脚本不执行**（页面只剩转圈的遮罩）。

## 2. 架构：数据源可插拔

```
① 采集层  EventSource（可替换）
            ├─ MockSource     演示：脚本回放 + 预置种子
            ├─ ManualSource   演示：现场手动上报  ← 最有说服力
            └─ RealSource     真实：App HTTP 上报
                │
② 接入层  API 网关 · 上报 / 增量拉取 / WebSocket 推送
                │
③ 处理层  抽取 → 锚点匹配 → 时空去重 → 可信度核查 → 发布
                │
④ 数据层  Postgres+PostGIS（事件/证据/轨迹格网） · Redis（去重窗口/在线状态） · 对象存储（图片）
                │
⑤ 呈现层  3D 地图打点 · 信息流卡片 · 探查任务
                │
⑥ 反馈层  「我也看到了 / 已通过 / 已清理」→ 回到 ③ 调整事件状态
```

**核心原则**：演示数据与真实数据**走同一条管线**。切数据源只改采集层，③④⑤⑥ 一行不动。

## 3. 定位子系统（自动 + 手动覆盖）

### 3.1 三种来源，同一结构

| 来源 | 实现 | 用途 |
| --- | --- | --- |
| `AutoProvider` | 脚本巡航路径（可复现）／随机游走（仅用于交代热度数据来源） | 默认；蓝点随移动自动更新 |
| `BeaconProvider` | 扫码 / 靠近智慧灯杆·环廊传感立柱 → 直接锁定锚点 | 现场演示高潮；叙事上是"未来校园定位基础设施" |
| `ManualProvider` | 地图点选（**原型已有**：`app.js` 的 `btn-report`→`pickHandler`→`nearestAnchor`） | 评审上手；覆盖自动定位 |

★ 三者**必须输出同一种结构** —— 否则"手动标的位置"与"自动定位的位置"在时空去重时算不出空间距离：

```js
{ anchorId, anchorName, subLoc, x, z, source, confidence, ts }
```

### 3.2 仲裁规则

```
默认自动（蓝点）
   │  用户点地图任意位置
   ▼
手动覆盖（橙点）—— UI 明示「已手动指定位置 · 点此恢复自动定位」
   │  三个解除条件（任一命中）
   ▼
恢复自动（蓝点归位到当前位置）
```

**三个解除条件**
1. 点「恢复自动定位」
2. **完成一次上报后自动恢复**（单次有效）
3. 自动源报告移动超过 **80 m**（说明人真的在走）

★ **override 期间自动源继续运行、只是不生效**（`if (manual) return`）。这样解除时蓝点立刻回到真实当前位置，**不跳回起点重来**。

### 3.3 接口骨架

```js
// web-demo/src/location.js
export const SOURCE = { AUTO: 'auto', BEACON: 'beacon', MANUAL: 'manual' };

export function createLocationService({ anchors, mode = 'readonly' }) {
  let cur = null, manual = null;
  const subs = new Set();
  const emit = () => subs.forEach((f) => f(cur));

  // ★ 三种来源共用同一个打包函数 —— 结构一致是去重能成立的前提
  const pack = (x, z, source, confidence) => {
    const a = nearestAnchor(x, z);
    return { anchorId: a.id, anchorName: a.name, x, z, source, confidence, ts: Date.now() };
  };

  let t = 0;
  const timer = setInterval(() => {
    if (manual) return;                       // ★ 覆盖期间继续跑但不生效
    t += 1;
    const [x, z] = CRUISE_PATH[t % CRUISE_PATH.length];   // ★ 脚本路径，演示可复现
    cur = pack(x, z, SOURCE.AUTO, 0.9);
    emit();
  }, 1000);

  return {
    getPosition: () => cur,
    subscribe(f) { subs.add(f); f(cur); return () => subs.delete(f); },
    setManual(x, z) { manual = pack(x, z, SOURCE.MANUAL, 0.7); cur = manual; emit(); },
    resumeAuto() { manual = null; },
    isManual: () => !!manual,
    beaconAt(anchorId) { manual = null; /* 扫码/靠近灯杆 → 锁锚点 */ },
    stop() { clearInterval(timer); },
  };
}
```

### 3.4 位置来源进可信度评分

上报时带 `position_source`，进可信度加权：

| 来源 | 权重 | 理由 |
| --- | --- | --- |
| `beacon` | **+0.08** | 物理在场，最强信号 |
| `auto` | 0 | 基准 |
| `manual` | **−0.05** | 防止乱标位置 |

### 3.5 合规

- 不做真实定位追踪；`RealProvider` 只保留接口不实现（`navigator.geolocation` 默认不调）
- 位置采样**格网化脱敏**后才上传，不上传原始轨迹
- 页面角落标注「演示数据」

## 4. 界面交互形态（三层分离）

### 4.1 输入层 —— 让"选位置"而不是"打位置"

| 交互 | 说明 |
| --- | --- |
| **长按 / 点选地图** | 主入口。弹出快捷上报面板，**位置字段已自动带出**「第三食堂 · 东侧道路」 |
| 一句话描述 | 自然语言（"三食堂门口停了辆卡车，过不去了"） |
| 位置可改 | 用户可重新选点 → 进入手动覆盖 |
| 可选附件 | 拍照 / 短视频（P3，先留接口） |

★ 关键设计：**地点由地图带出，不由用户输入**。这样地点从一开始就是结构化的，后面的时空去重才成立。

### 4.2 处理中 —— 必须可见

复用现成的 `AI_STEPS`（`events.js`）：语义解析 / 分类打标 / 去重比对 / 可信度评分 / 发布上线。
每步 0.4~0.9 s 逐步点亮，**这是整场演示最有说服力的 3 秒**，不要让它一闪而过。

### 4.3 呈现层 —— 分级，不是全打点

| 元素 | 规则 |
| --- | --- |
| 地图标记 | 脉冲环 + 光柱 + 类型色标签（`createEventMarker` 已有） |
| **聚合计数** | 同一事件 12 人上报 → **聚成 1 个点** + 「12 人上报」角标，点开才展开原文与上报人列表 |
| 信息流卡片 | 类型色 / 地点 / 可信度 / 时间 / **原文引用片段** |
| **可信度分级** | 高 → 正常打点；中 → 降透明；**安全类未核实 → 灰色虚标，不打点** |
| 时间衰减 | 事件有半衰期，过期降透明 → 移入「已结束」 |

★ 可信度分级对应需求基线 §九 点出的**法律风险**：发布错误的安全预警要担责。安全类事件可信度低于阈值时**进人工审核队列，前端只显示"待核实"**。

## 5. 处理管线

```
上报
 │
 ├─ ① 约束解码 → 结构化事件
 │     Schema：{ 类型 / 地点锚点ID / 楼层 / 起止时间 / 严重度 / 证据类型 / 原文引用 / position_source }
 │     ★ 地点字段约束为 ANCHOR_* 枚举，不是自由文本
 │     ★ 必须同时输出「原文引用片段」—— 这是后面可信度评分的证据链，事后补不出来
 │     ★ 第一版 Schema 控制在 6~8 个字段（太细小模型会为满足约束而乱填）
 │
 ├─ ② 锚点匹配（三级）
 │     精确/别名命中 → 句向量相似度 → LLM 消歧（给定候选列表二选一）
 │     别名表人工维护（三食堂 / 第三食堂 / 3 食堂 / 三食）
 │     匹配失败 → 落到「校区级」模糊位置并降可信度，**绝不瞎猜坐标**
 │
 ├─ ③ 时空去重（三路取交）
 │     同一事件 ⟺ 空间 < 150 m **且** 时间差 < 45 min **且** 句向量余弦 > 0.78
 │     HDBSCAN 的 noise 标签 = 可信度先验（孤立上报打折）
 │     簇的「人数」是最强信号：5 人独立上报 ≫ 1 人上报 5 次（按 user_id 去重后计数）
 │     ★★ ②③ 顺序不能反：地点若是自由文本，空间距离算不出来，去重直接废掉
 │
 ├─ ④ 可信度核查（三路证据 → 三分类裁决）
 │     证据源：UGC 交叉（独立上报人数）+ 官方源 RAG（保卫处/后勤通知）+ 常识一致性（锚点存在性校验）
 │     裁决：支持 / 矛盾 / 无证据 → 映射 1.0 / 0.0 / 0.5
 │     ★ 分数必须是可分解的加权项，能打印贡献明细（评审会问"为什么是 0.73"）
 │     ★ 安全类走强制闸门：低于阈值不自动打点
 │
 └─ ⑤ 发布 → 写信息流 + WebSocket 推送 + 触发路网联动（见 §6）
```

## 6. 事件状态机与路网联动

```
上报 → 抽取中 → 待核查 ─┬─ 可信度 ≥ 阈值 → 已发布 ─┬─ 已清理 / 超时 → 已结束
                        │                          └─ 证据矛盾 → 可信度回落
                        └─ 可信度低 或 安全类 → 待核实（灰标，不打点）

已发布 且 type = traffic/blocking  →  blocked_edges += 该边  →  A* 重算
已结束 / 证据矛盾                  →  blocked_edges -= 该边  →  路线自动恢复
```

**实现要点**：★ **不改 `aStar()`，改图的构建**。
现在 `buildGraph()` 从静态 `ROAD_EDGES` 建一次；改成 `buildGraph(blockedSet)` 带一个动态屏蔽集合。
`aStar()` 一行不动。封路与解封是**同一套机制的两个方向**，不是两个功能。

```
buildGraph(blockedSet)  →  aStar(from, to)  →  computeRoadRoute()  →  smoothPath()
                        →  RouteRenderer.showRoute()   （RouteBand + RouteCore + RouteFlow 流动粒子，均已有）
```

**渲染对比**：原路线（灰虚线）+ 新路线（高亮 + 流动粒子）+ 一句 AI 说明（"原路线经三食堂东侧，该路段被占用，已改走 XX，多 120 m / 约 2 分钟"）。

## 7. 通行热度与主动探查

**目标**：从"人知道但没说出来"扩展到"**没人知道但数据知道**" —— UGC 众包 → 数据驱动的态势感知。

```
① 位置采样 → 路段计数
     位置 ping 吸附到最近路段（复用 nearestRoadNode 同一套函数）
     按 edge × 15 min 桶累加
     ★ 用「路段」而不是「格网」做桶 —— 路网已经有了，比格网更贴合

② 同时段基线
     近 7 天「同时间片」的**中位数**
     ★ 必须用中位数：一次运动会/开学能把均值拉高，之后天天误报

③ 异常判据
     连续 K 个时间片 < 基线 15% → 疑似中断
     可升级：稳健 Z-score（MAD）→ STL 分解残差 → 把 edge × time 当图信号用 STGNN 预测残差

④ 排除已知原因（★ 防误报闸门，必须有）
     官方封闭 / 施工通知（官方源 RAG）
     时段基线（夜间本来就没车）
     假期 / 极端天气
     已在 blocked_edges 里的边

⑤ 产出「建议核查」任务（★ 绝不自动发布"这条路有问题"）
     巡查派单：给保安/后勤推任务卡「东南 outer_se3→outer_se4 近 6 小时无人经过，请前往确认」
     众包悬赏：给附近学生推"路过帮看一眼"，附上报模板，回来算贡献积分
     官方源交叉验证：自动检索通知；无官方说明 → 升级为"待人工确认"
```

★ **演示期边界**：这一步只能演示"机制"，演示不了"效果"（没有历史基线）。
正当解法：**合成一段 7 天的通行日志**（虚量数据的正确用法），再往里注入一个异常，跑出告警。

## 8. 场景推演：餐厅门口卡车挡路

**场景设定**：用户在食堂附近报告"卡车挡路无法通行"。

### 8.1 定位怎么确定

虚拟定位场景下**不取 GPS 真值**。用户位置 = 他在地图上选定的**锚点 + 方位**（UI 显示「第三食堂 · 东侧道路」）。
落图时锚点坐标做方位偏移，再**吸附到最近路段**（`nearestRoadNode()` 已有）。

- `食堂`（建筑表）世界坐标 **(167.6, 43.0)**，入口朝北
- 最近路段 = **外环南段 `outer_s2 (0, 77.5) → outer_s3 (200, 77.5)`**，垂直距离 34.5 m

### 8.2 完整链路

```
① 一句话上报「三食堂门口停了辆卡车，过不去了」
② 约束解码 → { type: traffic, anchor_id: Canteen, severity: blocking, position_source: manual }
③ 锚点匹配 → ANCHOR_Canteen → 落图 → 吸附 outer_s2→outer_s3
④ 去重 + 可信度核查 → 10 分钟内 4 人上报 → 合并为 1 事件，可信度 0.86 通过
⑤ 封路 → blocked_edges += (outer_s2, outer_s3) → A* 重算 → 渲染对比
```

### 8.3 ★ 实测结果（在真实路网图上跑 A\*，97 节点 / 109 边）

| 方案 | 距离 | 段数 |
| --- | --- | --- |
| ① 现状，不封路（主校门→食堂） | **844 m** | 15 |
| ② 现状 + 封路 | **844 m** | 15 ← **封路完全无效** |
| ③ 补 3 条连接边，不封路 | **244 m** | 2 |
| ④ 补 3 条连接边 + 封路 | **364 m** | 7 ← 绕行 **+120 m（+49%）** |

**结论**：现状下直线仅 205 m 却要绕 **844 m**（绕行系数 4.1×），且**封掉食堂门口那段路距离一点不变** ——
最优路径根本不经过它。**必须先补连接边（见 §10），否则这个演示会当场失败。**

### 8.4 反向闭环

其他用户上报"已通过" → 证据矛盾 → 事件可信度回落 / 自动解除封路 → 路线恢复。
这条"矛盾证据"路径在演示里很有说服力。

## 10. ★ 前置修复项（动手前必须做）

对账实测发现三个缺陷，**其中前两个会直接导致演示失败**：

| # | 问题 | 实测证据 | 危害 |
| --- | --- | --- | --- |
| **1** | **锚点表是阶段 0 占位坐标，未随 R5/R6 同步** | 19 个 `ANCHOR_*` 中 **8 个偏差 > 60 m**，最大 119.7 m；`ANCHOR_Canteen` 与真实食堂差 **139 m** | ★「地点→锚点→150 m 空间去重」**整条链建在这张表上** |
| **2** | **中轴与南段外环之间无连接边** | 主校门→食堂 844 m（直线 205 m）；★ **封路后距离不变** | 封路演示**完全失效** |
| **3** | **生活区北排 4 栋 `entrance` 朝向反了** | 统一写 `north`，北排北侧是内环、南侧才是外环南段；★ **宿舍E→食堂 直线 68 m 算出 554 m** | 日常路径全错，**且不报错** |

**修法**
1. 锚点表从最终 `BUILDINGS`（或 GLB）**重新生成**；加自检「锚点到最近建筑 ≤ 60 m」
2. 补 3 条几十米级连接边：`axis_gate↔outer_s2`（44 m）、`outer_s3↔inner_e_s4`（74 m）、`outer_s2↔inner_w_s5`
   补完必跑 `_diag_plan.py`，判据「**路网穿楼相交面积 = 0**」
3. 生活区北排 4 栋（宿舍A / 研究生公寓 / 宿舍E / 宿舍F）改 `entrance: 'south'`
