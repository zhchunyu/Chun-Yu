## 一、★★ V9 为什么改（产品架构修正的结果）

V8 训练完验收时暴露了问题，用户据此定了产品架构。**V9 是这次修正的落地。**

### 修正 1：删掉 `mutual` 类 —— 互助不是"报事"

原 V8 有 5 类（safety/congestion/service/notice/**mutual**）。但互助类内容是：

```
有没有人一起拼车去机场
求借充电器用一下
求组队参加创业大赛
转让两张话剧票
```

**这些本质是"找人"，不是"报事"** —— 发到论坛板块就行，不需要 AI 提取、不需要落图。
⇒ **删除 245 条**，type 从 5 类改为 **4 类**。

### 修正 2：模型不该"猜"地点

V8 验收时发现：输入**完全没提地点**，模型却会编一个建筑名：

```
输入: 下周三下午有消防演练，会拉警报     ← 一个字没提地点
V8 输出: "building_name": "3号宿舍楼"    ← 凭空编的 ❌
```

**这很危险** —— 用户看到事件打在 3 号楼会困惑；更糟的是如果帖子其实带定位标签（"第二食堂"），
就会和模型编的冲突。

**根因**：训练集里几乎每条都有建筑名 ⇒ 模型形成"这格必须填"的习惯。
**`loss` 完全看不出来**（type 对、JSON 合法，loss 就低）—— 只有拿"信息不足的输入"试才暴露。

⇒ V9：清掉 20 条"无中生有"，并在 **instruction 里明确写"未提及地点填 null，不要推测编造"**。

### 修正 3：建筑名归一

`打印店`(26 条) 与 `校园打印店`(1 条) 并存 —— 同一地方两个名字。统一为 `校园打印店`。

## 六、★ 地点字段的真实定位（重要，别误解）

**当前所有建筑名都是"占位"**，接软件后会由真实数据替换。模型**只负责搬运**文本里明确写的地点：

```
文本写了地点  → 照抄
文本没写地点  → null（由系统用发帖人定位 / 帖子标签补）
```

**模型不该越权去猜系统已知的信息。** 如果模型擅自编地点，而帖子其实带定位标签 ⇒ 冲突。

### 完整链路（用户拍板：急救走快速通道）

```
用户输入
   ↓
① 意图分类（毫秒级）
   ├── 急救类 ──→ 快速通道（120/校医院）★ 不进提取 LoRA
   └── 一般事件 ──→ ② 提取 LoRA → JSON → ③ 系统补全 → ④ 推送/落图
```
