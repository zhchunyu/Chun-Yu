# 交接说明：地点字段的处理约定

> 写给接后端/数据库的同学。**核心一句话：模型输出的 `building_name` 不可直接采信，必须以建筑表为准。**
> 建立时间：2026-10-04

---

## 一、背景：模型会"编造地名"

提取 LoRA（V9）在**输入没提地点**时，不一定会输出 `null`，而是会**编一个看起来合理的建筑名**。

实测证据（V9，2026-10-04）：

```
输入: 有人晕倒了，快来人
输出: "building_name": "校医院"          ← 编的（语义联想：晕倒→医院）

输入: 宿舍楼下洗衣机全是坏的
输出: "building_name": "第一学生公寓A区"   ← 发明的名字（建筑表里 37 个没有这个）

输入: 有没有人今晚一起去操场跑步的
输出: "building_name": "中央公园"          ← 校园里根本没这地方
```

**null 正确率实测只有 50%**（2 条测试过 1 条）。

**根因**：训练数据里绝大多数样本都有地点，模型形成了"这一格必须填"的习惯。
补 null 样例能改善，但**不可能 100%** —— 这是大模型的固有行为，不要指望靠训模型根治。

⇒ **系统层面必须兜底。**

---

## 二、★ 必须遵守的约定

### 约定 1：`building_name` 只做参考，落图/展示必须过建筑表

```
模型输出 building_name
   ↓
查建筑表（后端维护的真实建筑清单）
   ├── 查到了 → 用**表里的** building_id / 名称 / 坐标
   └── 查不到 → **丢弃该字段**（视为 null），走约定 2
```

**⛔ 绝对不要**：直接把模型输出的 `building_name` 显示给用户，或直接拿去落图。
否则用户会看到"地点：中央公园"这种校园里不存在的地方。

### 约定 2：没地点时用发帖人定位兜底

```
building_name 为 null（或查表失败）
   ↓
用发帖人的 GPS 位置 / 帖子带的定位标签
   ├── 有定位 → 反查最近的建筑 → 落图
   └── 没有定位 → 事件进"待补地点"状态,只进列表,不落图
```

### 约定 3：匹配要用别名表，不要精确匹配

用户在文本里写的是简称，建筑表里是全称。必须做别名映射，否则会把对的判成错的：

| 用户写法 | 建筑表全称 |
|---|---|
| 澡堂 / 浴室 | 公共浴室 |
| 打印店 | 校园打印店 |
| 报告厅 | 学术报告厅 |
| 一食堂 | 第一食堂 |
| 北门 | 北校门 |
| 大活 | 大学生活动中心 |
| 活动中心 | 大学生活动中心 / 学生活动中心（**有歧义，需人工/上下文判定**） |

别名表见 `models/auv/model-finetune/data/build_v9_extract.py` 的 `ALIAS` 字典。

## 三、提取 LoRA 的职责边界（别让它干不该干的）

模型**只提取文本里明确写了的东西**。它的输出仅供下游参考，不是最终事实。

```
模型管：从文本抽 type / severity / description / 原始地点文本
模型不管：地点是否真实存在、地点是否可信、落图坐标
系统管：建筑表匹配、定位兜底、冲突消解、最终落图
```

### 冲突消解建议

当**模型从文本抽出的地点**和**帖子带的定位标签**不一致时：

| 情况 | 建议 |
|---|---|
| 文本有地点 + 帖子有定位，且一致 | 直接用 |
| 文本有地点 + 帖子有定位，不一致 | ★ **以帖子定位为准**（用户手动打标比文本推断可靠），但保留文本地点作为次级信息 |
| 文本无地点 + 帖子有定位 | 用帖子定位 |
| 都没有 | 不落图，进"待补地点" |

---

## 四、急救类的特殊处理（不进本管线）

用户已确认：**急救类走快速通道，不进提取 LoRA**。

```
用户输入 → 意图分类（轻量，毫秒级）
             ├── 急救类（有人晕倒/着火/受伤）→ 快速通道：立刻给应急指引（120/校医院）
             │                                    ★ 不排队等提取，不走 JSON
             └── 一般事件 → 提取 LoRA → JSON → 系统补全 → 推送/落图
```

判据：**"这条信息不推给附近的人，会不会有人吃亏？"** 会，才值得提取+推送。
