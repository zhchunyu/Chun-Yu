## 三、逐字段解读

| 字段 | 谁最强 | 说明 |
|---|---|---|
| **type** | **模型 10/10**（正则 9/10） | 模型唯一明确胜出的字段。正则漏了"校医院开的药好贵"（无 service 关键词） |
| **wait** | **正则 10/10** | 正则直接抓"40分钟/20分钟"数字；模型反而**瞎猜**（文本没提分钟数时给 23/25） |
| **window** | **正则 9/10** | 模型有**过度补全**倾向 —— 文本没提时间时硬猜 noon/evening，而期望是 `unknown` |
| **severity** | **三路全 5/10** | ★★ 见下 |

### ★★ severity：三路全卡 50%，问题不在方法，在口径

正则 5/10 · 14B 基础模型 5/10 · 训练过的 LoRA 5/10 —— **三个完全不同的方法给出同一个分数**，
说明**这不是能力问题，是标注定义问题**。模型一律倾向"填满"（总给 high/medium），
而期望里大量是 `null`。

⇒ **处置建议：要么给死规则（按关键词映射），要么从产品里砍掉这个字段。**
继续为它训练是浪费。

### ★ 标注本身有错，削弱了对比可信度

第 7 条 `"谷园2楼新开的窗口超好吃但排队40分钟"`，期望 `window = "noon"` ——
**文本里根本没提中午**。按"没提就 unknown"的口径，这条期望应是 `unknown`。
这类错误让**保守输出 `unknown` 的正则占了便宜**，也让模型"猜 noon"显得更错。

**⇒ 10 条样本 + 有错的标注，不足以支撑"训练无用"的终审结论。**
但"severity 该砍""地名该交数据库"这两条，结论足够硬。

## 五、三个必须处理的问题

### 1. ★★ 提取 LoRA 不会拒答 —— 意图分类必须前置

C 组两条（故意不该提取的）**全失败**：

| 输入 | 性质 | 输出 |
|---|---|---|
| 有没有人今晚一起去操场跑步的 | 互助 | `notice` + `操场` |
| 感觉这学期什么活动都没赶上，有点失落 | 情绪 | `notice` |

模型**任何输入都硬吐 JSON**，不会说"这条不该提取"。
⇒ 坐实了产品链路里 **① 意图分类必须放在提取 LoRA 之前**，不能指望模型自己判断。
（这正是你拍板的链路设计，现在有实测支撑了。）

### 2. ★ 套话换了新马甲，旧判据抓不到

`check_v10.py` 的 GENERIC 列表（"存在安全隐患"/"服务调整"/"请注意时间安排"/"互助信息发布"）
**已过时**。V10 输出的新套话形态：

- "3号公寓楼设备故障，暂停使用"
- "崇文楼近期将举办活动"
- "操场晚上将举办活动"
- "近期无大型活动安排"

⇒ 判据要更新为**形态匹配**（"…将举办活动"/"…设备故障，暂停使用"），不是枚举字符串。

### 3. 睿智文体馆 type 判错（有争议）

"羽毛球场地今晚约满了" —— 期望 `congestion`，模型给 `service`。
**这条本身就有争议**：场地约满算"拥堵"还是"服务"？标注口径需要定死，否则永远算错。

## 六、结论

| 问题 | 答案 |
|---|---|
| **V10 训成了吗？** | **成了。** 地点合法率 100%，id 全对，旧校区名清零 |
| **V10 值得保留吗？** | **值得。** 它是「后端能对上权威表」的前提，不是可选项 |
| **还要为地名扩数据吗？** | **不要。** 地名是数据库的活（字符串+别名 81%），模型只负责"搬运" |
| **还要继续训吗？** | **先别。** 三路对比里正则 82% 最高，模型只在 type 上领先 1 条 |
| **下一步做什么？** | ★ **修标注，不是修模型** —— severity 口径 / window 的 unknown 语义 / type 争议项 |

**一句话**：V10 解决了它该解决的问题（地点合法），但"训练能不能提升整体提取质量"
这个问题**目前无法回答** —— 因为**标准答案本身没定好**。
