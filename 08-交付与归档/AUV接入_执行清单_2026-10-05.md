## 2 ★★★ 三个阻塞（按这个顺序处理）

### 阻塞 ①：服务根本没在跑 —— 这就是队友看到的 AutoDL HTML 404

**诊断依据（很硬）**：`/docs` 是 FastAPI **自带**的页面，**不需要鉴权**。
- 它返回 **HTML 404** ⇒ 请求根本没到达 FastAPI ⇒ **6006 端口上没有后端在监听**（AutoDL 网关自己兜了个 404 页面）。
- 如果只是密钥错，会返回 **401 JSON**；如果只是路径拼错，`/docs` 会返回 **200 Swagger 页面**。
- ⇒ 队友那句「这与根路径正常返回 JSON 404 不同」判断得很准，方向就是「服务/端口」。

**在服务器上依次跑：**

```bash
# 1) 进程还在不在
ps aux | grep -E 'llamafactory|vllm' | grep -v grep

# 2) 到底谁在监听 6006 / 8000
ss -ltnp | grep -E ':6006|:8000'

# 3) 卡在不在（无卡模式下 GPU 不可用，服务起不来 —— 这是预期行为）
nvidia-smi

# 4) 本机自测（★ 这一步过了才谈公网）
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:6006/docs
```

> ★ 端口必须是 **6006** —— AutoDL「自定义服务」只映射这一个口。
> 如果第 2 步显示服务在 **8000**，那就是根因：**重启到 6006**。

### 阻塞 ②：不是「key 不一致」，是「要确认服务器用的就是这个 key」

- 包里 `.env.auv-secrets` 的 `AUV_API_KEY` 是 **`auv-（完整值见 .env.auv-secrets）`**（47 字符 = `auv-` + 43）。
- 已核对：**这个格式正是** `python -c "import secrets;print('auv-'+secrets.token_urlsafe(32))"` 的输出
  ⇒ 确认它就是**你在终端生成、发过去的那个 key**，方向没错。
- **风险点在服务端**：`start_api.sh` / `serve_vllm.sh` 里的**默认值是 `auv-CHANGE-ME-2026`**。
  如果你起服务时**没有显式带上 `API_KEY`**，服务器上跑的就是那个占位值 ⇒ 队友会收到 **401**（不是 404）。

**处理**：起服务时显式带上包里的完整值（下面 Step 2 / Step 3 已写进去）。
★ 顺序上**先定 key、再起服务**，省得起了又停。

> ★ 三个地方必须是**同一个值**：① 服务器启动时的 `API_KEY` ② 包里的 `.env.auv-secrets`
> ③ Supabase 的 `AUV_API_KEY` Secret。任一不同 ⇒ 401。
> ★ 建议顺手把 `start_api.sh` / `serve_vllm.sh` 里的默认值直接改成你的真 key，
> 免得以后忘记 export 又踩一次。

### 阻塞 ③：persona 挂不上 —— 路 A 做不到（★ 源码级结论）

队友的代码靠 **`model` 名**区分：`extract` 抽 JSON、`persona` 说话。
但 **LLaMA-Factory 自带的 API（路 A）不读 `model` 字段**。官方源码 `src/llamafactory/api/app.py`：

```python
@app.get("/v1/models", ...)
async def list_models():
    model_card = ModelCard(id=os.getenv("API_MODEL_NAME", "gpt-3.5-turbo"))
    return ModelList(data=[model_card])            # ← 永远只返回一个名字

@app.post("/v1/chat/completions", ...)
async def create_chat_completion(request: ChatCompletionRequest):
    return await create_chat_completion_response(request, chat_model)   # ← 不读 request.model
```

⇒ **路 A 一个进程只能挂一个 LoRA**。给 `model: "persona"` 会**静默用 extract adapter 回答** ——
**不报错、但人设失效**，属于最难发现的那类问题。

| | 路 A（`llamafactory-cli api`） | 路 B（vLLM） |
|---|---|---|
| 按 `model` 名切 LoRA | ❌ **不支持** | ✅ `--lora-modules extract=… persona=…` |
| 同时服务 extract + persona | ❌ | ✅ |
| 要装新东西 | 不用 | 装 vLLM + 下 AWQ 基座（~9.5 GB） |
| 今天能用 | ✅（只验一个） | 等下载 |

> ★★ **所以要给队友「同时能用的 extract + persona」，只能走路 B。**
> 早先写「两条路协议一样、队友代码不用改」**只说对了一半** —— 协议格式确实一样，
> 但**能按 model 名切 adapter 的只有路 B**。这条已在 `部署清单.md` §0.5 和 `start_api.sh` 里改正。

**建议节奏**：
1. 今天先用**路 A + extract** 验证「事件分析」链路（产品链路第一环），给队友一个确定答复；
2. 同时后台下 AWQ 基座；
3. 下载完切**路 B**，persona 一起通，再让手机端做真实联调。
