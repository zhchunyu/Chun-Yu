# 一 产品概述与定位
## 1 研发背景与目标
校园生活中的地点、服务、交流和课程安排通常分散在不同入口。新生寻找建筑、同学选择餐厅、查看附近设施或交流校园情况时，需要反复切换地图、聊天和信息页面。AI 可以帮助解释信息和整理计划，但建议必须关联到实际地点与可靠资料。

Our Campus 围绕本校区本校区，构建面向安卓手机的校园服务应用。当前产品目标是形成“地点可查、路线可用、交流可同步、建议可核对”的日常使用流程。数字孪生在现阶段体现为校园地点与软件业务的关联，不宣称已经完成实时传感器接入或全校园三维复刻。

## 2 用户与入口
| 用户 | 已有入口与能力 | 使用边界 |
|---|---|---|
| 访客 | 地图、地点搜索、服务与部分原型页面 | 真实聊天与 AI 调用需要登录 |
| 学生 | 邮箱账号、实时大厅、个人课表、地点导航 | 邮箱注册不等于学校学籍认证 |
| 管理者 | 服务器角色；餐厅窗口增删接口及原型管理界面 | 云端权限由服务器校验；本机管理不等于学校工单 |

底部使用首页、地点、大厅、我的四个入口。首页保持地图主界面；地点集中搜索与附近设施；大厅容纳聊天、热点、失物和餐厅评价；个人中心承载账号、课表、收藏及本机发布管理。

## 3 与 AI 的结合
AI 入口位于大厅顶部。校园建议使用当前地点资料与可读取的有效事件；事件分析把用户主动描述整理为草稿；课表页面把所选周课程带入可编辑输入框。用户确认后才发送给 AI，不默认读取其他同学聊天或持续采集位置。

# 二 技术架构与创新
## 1 当前系统架构
前端采用 React 与 Vite，使用 Capacitor 封装为安卓软件。业务数据直接通过 Supabase SDK 在用户会话和行级权限约束下访问；AUV 请求经过可信服务端验证身份，再调用模型接口。原型业务与个人课表保存在本机，尚未全部迁移到数据库。

[diagram:architecture]

图 2 当前软件架构。实线框为现有组件，底部列出尚未上线的扩展能力；AI 不直接写入审核结果或通知收件人。

## 2 数据交互边界
账号与大厅消息使用云端持久化；页面实时变化通过 Realtime 同步。模型密钥仅在服务器读取，客户端携带当前用户的登录凭据。地图请求使用腾讯地图配置，定位调用设备能力；本机课表在用户点击发送前不上传模型服务。

本机开发使用 Vite 的 Node 中间件转发 AI 请求；手机构建默认调用 Supabase Edge Function，也支持配置独立 HTTPS 网关。当前没有实现原稿所述的统一异步分析任务队列、事件记忆服务和通知投递编排。

## 4 云端结构与本机数据
云端脚本包含地区、地点、个人资料、消息、事件、失物、设施贡献、反馈、通知及服务信息等对象。当前 App 已实际连接账号、聊天和餐厅窗口；其他业务表存在于设计或迁移脚本中，并不代表对应界面已经读写云端。

角色单独保存在私有权限表，通过 campus_my_role 读取。工程整理了 66 个校园地点 ID，用于地点卡片与 AI 匹配；坐标、别名和来源仍需要持续核验，不能把静态目录称为学校官方实时数据库。

# 二 技术架构与创新
## 5 AUV 调用与任务分工
校园建议模式把用户问题、最多最近 6 条对话、可选地点、校园目录、服务信息和可读取的有效事件组装为上下文，调用 persona。服务端查询事件时限定非演示、active 且有效时间内；查询失败时明确告知缺少动态数据，未查询到事件不代表校园不存在情况。

事件分析模式调用 extract。紧急关键词先进入确定性应急提示；互助或失物描述引导到大厅；普通排队、施工、故障和通知等描述才进入事件提取。关键词规则是当前实现，不宣称拥有经测定的意图分类准确率。

[diagram:ai]

## 6 已实现的可靠性处理
服务端向 Auth 核验会话后才调用模型。输入正文限制为 1-1000 字，校验 mode 与地点 ID；模型调用配置 45 秒超时，前端保留失败草稿。JSON 无效、模型鉴权失败、网络中断或空回复均返回明确错误，不生成虚假成功结果。

单实例采用单用户并发限制、每分钟请求次数限制和总并发上限。该机制属于代码级保护，不是负载测试结论；多实例部署仍需要共享限流服务。

AI 当前响应用户主动请求，事件结果只作为草稿返回。不会持续分析全大厅消息、自动审核发布、自动执行计划或发出后台通知。

# 二 技术架构与创新
## 7 模型输出与软件采信规则
提取提示要求模型返回九个字段。运行时不直接采信整份 JSON，而由业务代码重建软件可用的结果。

| 字段 | 当前处理方式 |
|---|---|
| type | 限定 safety / congestion / service / notice；不合法则拒绝 |
| building_id、building_name | 由原文正式名称或有效别名匹配，或用户手动选点确定；忽略模型自报地名 |
| floor | 仅保留原文中出现的楼层字符串；缺失为 null |
| severity | 提示词要求输出；当前网关返回对象未保留，不用于自动风险决策 |
| description、advice | 截断长度，作为摘要与建议展示；不作为已核实事实 |
| estimated_wait_min | 当前网关强制置 null，不用模型估计作为导航耗时 |
| time_window | 仅接受约定枚举；无效值返回 unknown，不推断精确日期 |
| location_status | 网关补充 selected / text_match / ambiguous / missing |

例如“宿舍楼下洗衣机坏了”不能唯一定位某栋公寓；“图书馆与禾香都很挤”涉及多个地点，结果保持歧义，要求用户确认。模糊的“食堂”“教学楼”等别名不能单独绑定建筑。

## 8 本项目的工程创新与差异化
以稳定地点 ID 将地图、服务、社区入口和 AI 地点动作关联起来，建议可以直接转入查看地点或导航。课表导入采用本机预览和明确发送，让课程时间进入 AI 输入，同时保留用户核对与控制。

任务路由与事实校验分工：模型整理语义，代码决定可采信的地点与字段，缺失信息显式保留。校园相关性评分、事件聚合和主动推送是下一阶段设计，尚无实现结果或比较实验，不作为当前创新成果统计。

# 三 功能设计与实现
## 1 地图、标签与地点卡片
首页以腾讯 2D 地图为主要空间界面，支持拖动、缩放、旋转和恢复位置。校园内地点点击后打开软件设计的详情页面或卡片，提供名称、服务信息、收藏、反馈及路线入口；不把手工标签位置直接冒充腾讯原生 POI 精度。

地点列表按类别搜索，并提供附近设施入口。外部官网按钮按已有地点配置跳转。服务开放时间、电话等缺失时保持未知或提示以现场及官方信息为准，页面不补造学校实时数据。

## 2 前台定位
用户点击定位后，由 Capacitor Geolocation 检查和申请权限，获取经纬度、精度与时间戳，在地图显示位置并移动视角。拒绝权限、定位服务关闭或超时都有对应提示。当前没有后台持续定位或学生轨迹库。

设备位置与地图坐标转换分开处理：腾讯地图使用 GCJ-02；本机平面图采用比例坐标；三维资产采用独立局部坐标。坐标之间通过明确转换或地点 ID 关联，不能直接混用。

## 3 两类路线能力
腾讯步行规划请求 from/to，解析压缩路径、距离、预计时长与步骤，绘制路线。手机通过 qqmap 导航 URI 调用腾讯地图，网页可使用 HTTPS 路线入口；逐步导航由腾讯地图承载，不是本 App 自研导航 SDK。

工程另保留本地 A* 路网及最短、无障碍、避施工、避雨、夜间五种模式。其道路属性属于既有演示数据，尚未完成真实本校区测绘与通行核验，不能声称腾讯路线已实现上述偏好约束或实时施工绕行。

# 三 功能设计与实现
## 4 真实账号
“我的”提供邮箱与密码注册、昵称登记、邮箱验证、登录、重发验证邮件、密码重置、修改昵称与退出。软件支持输入数字邮箱验证码；邮件实际内容、有效期及可接收邮箱范围由服务器 Auth 与 SMTP 配置决定。手机号与校内统一认证尚未正式接入。

用户会话由 Supabase SDK 保存和刷新。密码、验证码不写入本机业务数据；管理角色从服务器 RPC 读取，不能通过修改昵称或用户自报角色升级为管理员。

## 5 大厅消息
真实聊天内容写入 hall_messages。地区包括教学区、生活区、宿舍区、运动区和校门周边；“全部”是查询视图，不是消息的地区值。每页读取 50 条历史，使用服务器时间与 UUID 游标加载更早记录。

发送后以数据库成功响应为准，再清空草稿。client_message_id 在失败重试时复用，并结合作者唯一约束处理重复插入。昵称从 profiles 读取，撤回仅允许操作本人消息。

[diagram:chat]

Realtime 订阅插入、更新和撤回，重新连接或回到前台时补读最近消息；前台联网时每 30 秒轮询补偿。连接状态显示真实的在线、离线或重试中，不把轮询误称为始终实时。

已有真实账号和多作者消息运行记录；完整双手机断线、撤回及权限回归仍需逐项留证。当前不包含私聊、群管理、聊天附件、在线人数、消息中心或安卓后台消息推送。[3]

# 三 功能设计与实现
## 6 大厅中的生活服务
聊天、校园热点、失物招领与餐厅评价位于同一级，避免继续增加底部导航入口。热点与失物复用地区筛选，关联地点后可以查看或规划路线。现阶段热点、失物和设施数据仍为本机原型。

失物招领支持寻物／招领、搜索、照片、联系说明以及编辑、完成、重开和删除。“我的发布”集中管理本机条目。不能因使用真实登录账号就宣称帖子已经同步给其他设备；联系信息也不自动供 AI 读取。

## 7 餐厅与窗口评价
覆盖禾香餐厅、教工餐厅、悦膳餐厅和桃李餐厅。可由大厅进入餐厅列表，或由地点详情打开专用评价页面。餐厅页面按窗口展示，并提供分类、搜索、星级、评价标签及价格等交互。

| 对象 | 当前实现 | 数据边界 |
|---|---|---|
| 餐厅目录 | 四个稳定餐厅 ID 与地点关联 | 本地配置，不代表全部真实窗口已录入 |
| 窗口名单 | restaurant_windows 云端接口 | 本次只读查询成功，当前为 0 条；可开始录入 |
| 管理员增删 | 前端 RPC 检查与 SQL RLS 策略 | 普通用户无增删入口；实际写权限尚需双角色验收 |
| 同学评价 | 窗口详情、写评价与本机保存 | 未实现多人共享、云端统计与审核；示例评分明确标识 |

同餐厅窗口编号唯一，允许编号包含楼层；不同餐厅可复用编号。空窗口名单应显示尚未收录，不能用示例填成正式窗口。删除窗口不会声称已删除其他设备的历史评价。

后续多人评价需要新增用户归属、审核与举报、编辑历史及服务端统计；当前不会把本机星级视为全校同学的真实口碑。

# 三 功能设计与实现
## 8 本机课表导入
入口为“我的 → 教务与学习 → 我的课表”。支持本校区当前教务导出的 BIFF8 .xls 学生个人课表，文件上限 4 MB。流程为选择文件、解析预览、核对课程与缺失信息、确认替换；失败保留旧课表。

周次可以是连续范围或离散列表，单格多门课程分别读取。没有具体时间的课程单独提示，不填造星期、时段或教室。首版不支持任意学校模板、.xlsx、加密文件、公式单元格或需跨记录读取的超长字符串。

真实文件解析记录：9 门有明确时间的课程、21 条安排、6 个时段；另有 1 门缺少具体时间。第 4 教学周展开为 11 条课程。上述为单个文件的工程检查，不是对各校 Excel 通用识别率的评估。

## 9 学期日期与个人数据
导入后的课表按账号或访客分别保存在本机，不保留表头的姓名、学号和班级标题。换手机需要重新导入；没有接入课表云端同步。课程中的教室编号尚未自动映射地图建筑。

当前录入起始日期为 2026-08-30，但该日是周日，与“第 1 周周一”不一致。软件保留输入并提示核对，当前只按教学周查看；在确认有效周一起始日期前，不展示推算出的今日课程，也不按实际日期提醒。

## 10 AI 规划联动
“让 AI 规划本周”把所选周课程名称与时间生成最多 1000 字的草稿，打开 AUV 输入框。用户可以检查并补充学习目标后发送，不自动上传整份原文件、姓名或学号，也不把 AI 建议自动写入日历。

企业微信或学校教务系统尚未授权接入。当前路径是用户自行导出并导入课表；自动查询成绩、考试与教务通知属于后续授权合作范围。

# 五 应用价值与展望
## 1 当前可演示的实际场景
寻找校园服务：同学在地点页搜索图书馆、校医院或餐厅，查看可用资料和官网入口，点击路线后使用腾讯地图导航。信息和导航共享地点标识，减少重复搜索与复制地点的操作。

校园交流：学生通过真实账号进入大厅，按校园区域交流。同一用户在另一设备登录可读取云端聊天历史；热点、失物和评价目前仍须提示是本机原型，不能用它们证明全校信息共享。

描述现场问题：同学输入具体地点的排队或故障情况，AUV 整理事件草稿并给出关联地点动作。草稿仍是用户描述，未核实、未发布；这一过程可作为后续管理员核验流程的输入。

# 五 应用价值与展望
## 3 成果总结与产品定位
当前软件形成了可安装安卓应用、腾讯地图地点与导航、邮箱账号、区域实时聊天、AUV 可信调用和个人课表导入的核心组合。软件侧贡献在于地点关联、任务路由、事实字段校验、用户确认流程及多端工程集成。

目标市场首先是单校园的小范围使用与验证。项目暂未提供学校正式合作、用户规模或市场营收材料，定位为持续迭代的校园应用，不宣称已经覆盖全校或具备官方服务身份。
