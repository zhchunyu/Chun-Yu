# 07 · 技术路线与架构

> 面向要接手或扩展这个项目的同学。读完你应该能回答：
> **为什么这么选？系统分几层？数据从哪来到哪去？哪些地方可以改、哪些是硬约束？**

## 1. 需求与约束

项目一开始的需求只有"做个校园 2D 导航地图"，但随着协作方式明确，实际约束变成了三条：

| # | 约束 | 对技术选型的影响 |
|---|------|------------------|
| C1 | **主要用 AI 工具开发** | 源文件必须**纯文本、可 diff、可 grep**；不能有 GUI 工程文件、二进制中间产物、需要点界面才能改的东西 |
| C2 | **校园是虚拟构建的** | 不需要地理配准、不需要卫星影像、不需要投影——经纬度本身都可以不要 |
| C3 | **最终要并入三维数字校园** | 2D 与 3D 必须**共用一套坐标系和一套数据**，不能各搞一套 |

这三条约束直接否掉了项目最初的方案。

## 2. 技术路线演进

### 方案A：GIS 工具路线（已退役）

```
QGIS 数字化 → 导出 GeoJSON(EPSG:4326) → geojson_to_graph.py → graph.json
                                              ↓
                          Leaflet + Esri 卫星影像瓦片 + PyInstaller exe
```

曾经真的跑通过，也真的抓了 832 片校园卫星影像。但它同时违反 C1 和 C2：

| 资产 | 问题 |
|------|------|
| QGIS 工程（`.qgz`） | 压缩二进制，AI 完全读不了，也改不了 |
| 832 片 JPEG 瓦片（9.9 MB） | 二进制图片，AI 读不了、diff 不了 |
| 两个 `.exe`（18.6 MB） | 打包产物，看不到逻辑，改一行要重新打包 |
| Leaflet（147 KB） | 外部依赖，是 AI 改不动的黑盒 |
| 经纬度 + 仿射标定 | 虚拟校园根本不需要，纯属成本 |
| 卫星影像 | 虚拟校园没有真实影像可用 |

结果：项目 94.4 MB，其中 94 MB 是 AI 无法参与的部分。

### 方案B：纯前端 SVG 路线（现行）

```
data/campus/*.json  ─build_graph.py─▶  data/graph.json
        │                                     │
        └──────────────┬──────────────────────┘
                       ▼
              web/geo.js（纯逻辑层）
              坐标变换 · 多边形 · Dijkstra
                       │
                       ▼
              web/app.js（渲染层）
              原生 SVG，每个要素 = 一个 DOM 节点
```

项目体积 **94.4 MB → 0.34 MB**，且**全部是纯文本**。

## 3. 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│  数据层  data/campus/*.json          ← 人/AI 手改，唯一真源    │
│  平面米坐标 · buildings / roads / footways / nodes            │
└───────────────────────────┬──────────────────────────────────┘
                            │  scripts/build_graph.py（Python，仅标准库）
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  图数据层  data/graph.json           ← 派生产物，不要手改       │
│  nodes[{id,name,x,y}] · edges[{from,to,weight,geometry}]      │
│  adjacency{...}（双向邻接表）                                  │
└───────────────────────────┬──────────────────────────────────┘
                            │  fetch()
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  逻辑层  web/geo.js                  ← 纯函数，浏览器/Node 双用 │
│  坐标变换 · 多边形几何 · 最小堆 · Dijkstra · 路径拼接           │
│  ★ 没有 DOM、没有依赖 → 可以用 node 直接断言正确性              │
└───────────────────────────┬──────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  渲染层  web/app.js + index.html + style.css                  │
│  原生 SVG：缩放/平移 = 改 viewBox；要素带 data-* 语义属性       │
└───────────────────────────┬──────────────────────────────────┘
                            │
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
   2D 浏览器页面                        3D 场景（Three.js / Babylon）
   （本项目 web/）                     （见 docs/08，复用同一份数据与 geo.js）
```

**关键分层原则**：

- **逻辑与渲染严格分离**。凡是"算"的（坐标、最短路、多边形）都在 `geo.js`；
  凡是"碰 DOM"的都在 `app.js`。前者可断言，后者不可。
- **数据与渲染无关**。`graph.json` 不知道自己是给 2D 还是 3D 用的。
  这就是 C3 能成立的原因：3D 直接消费同一份文件。

## 4. 数据流

```
① 编辑数据        data/campus/buildings.json 等（人或 AI 手写 JSON）
                          │
② 生成图          python scripts/build_graph.py
                  - 读 nodes.json 建命名节点
                  - 读 roads/footways.json 按 from/to 连线
                  - 权重 = 平面欧氏长度（米）
                  - 连通性自检
                          ▼
③ 前端加载        web/app.js  fetch → data/graph.json + data/campus/*.json
                          │
④ 坐标变换        geo.js  makePlanarProjection()：y 轴翻转成 SVG 方向
                          │
⑤ 渲染            app.js  生成 <polygon>/<polyline>/<g class="node"> 等 DOM
                          │
⑥ 交互            点选起终点 → geo.js dijkstra() → 高亮路线 + 面板数据
```

**唯一真源是 `data/campus/*.json`**。其它一切都是从它推导出来的。
这条规则让协作变简单：不会出现"谁的地图数据才是对的"这种问题。

## 5. 关键设计决策

| 决策 | 理由 | 被否决的选项 |
|------|------|--------------|
| **原生 SVG 手写渲染** | 要素即 DOM，可 CSS 定制、可 grep、可加事件；零依赖 | Leaflet / Canvas / 地图库——都是"改不动的黑盒" |
| **平面米坐标** | 校园是虚拟的；坐标即米，边长用勾股定理，无需投影 | 经纬度 + 仿射标定（成本高、无收益） |
| **`geo.js` 浏览器/Node 双用** | 算法可在命令行断言，正确性不依赖人眼 | 直接把逻辑写进 `app.js`（只能靠肉眼验证） |
| **`.json` 而非 GeoJSON** | GeoJSON 规范要求 WGS84 经纬度，写平面米是违规的，会误导工具 | 沿用 `.geojson` 后缀（工具会误解释） |
| **`graph.json` 为派生产物** | 单一真源，避免图与数据不一致 | 手维护 graph.json（改数据后必然漂移） |
| **`.bat` 而非 exe** | 纯文本、可读可改；exe 是黑盒 | PyInstaller 打包（改一行要重新打包） |
| **零依赖** | 离线可用；没有 `node_modules`/`.venv`；AI 不会误判依赖 | npm/pip 生态（对这个规模是负担） |
| **要素带 `data-*` 属性** | 路线算得对不对，读 DOM 属性就知道，不必数像素 | 只靠视觉呈现（AI 无法核验） |
| **验证脚本作为门禁** | 57 项断言，退出码即结论，可直接进 CI | 靠人工点击测试 |

### 关于"为 AI 友好"到底做了什么

这不是口号，是具体机制：

1. **算法可断言**：`web/geo.js` 无 DOM 依赖 → `node web/verify.js` 能跑 57 项断言。
2. **语义化 DOM**：
   ```html
   <g class="route" data-from="south_gate" data-to="E1"
      data-distance-m="468.2" data-nodes="south_gate>cross_main>...">…</g>
   ```
   路线对不对，**读属性就知道**，不需要截图判断。
3. **一致性断言**：`verify.js` 第 3 节专门检查 `graph.json` 与源数据是否同步——
   这是 AI 协作最容易犯的错（改了数据忘了重建图）。
4. **文档即契约**：本文档、`docs/06`（数据规范）、`docs/08`（3D 契约）里的每条约定，
   在 `verify.js` 里都有对应断言兜底。文档和代码不会各自漂移。

## 6. 性能与规模

| 指标 | 当前值 | 说明 |
|------|--------|------|
| 节点 / 边 | 17 / 19 | 演示校园规模 |
| 最短路单次 | ~0.001 ms | 二叉堆实现；5000 次查询 7 ms |
| 全节点对（136 对） | 可忽略 | 验证脚本每次都跑全量 |
| 页面首次加载 | < 1 MB | 全部文本，无外部请求 |
| 项目总体积 | 0.34 MB | 46 个文件 |

**已知瓶颈不在算法，在渲染**：当前是"一次性渲染全部要素"。
校园放大到上千节点/建筑时，需要加视口裁剪（只渲染 viewBox 内的要素）。
算法侧余量很大（0.001 ms/次），不用动。

## 7. 演进路线

已经做完的：

- ✅ 平面米坐标数据层 + 建图脚本
- ✅ 零依赖 SVG 渲染 + 交互
- ✅ 57 项自动化断言（含 3D 对接契约）

可以继续做的（按价值排序）：

1. **用 SVG 文件本身当数据源**：把校园平面图直接写成 `.svg`（带 `id`/`data-*`），
   再用小脚本派生 `graph.json`——让"底图"和"数据"是同一个可读文本，
   画图和改数据变成同一件事。
2. **建筑高度数据化**：现在高度靠 `floors × 3.5` 推导，应逐步补上真实 `height`。
3. **室内楼层**：节点加 `floor` 字段，垂直连接用 `type: "elevator"/"stairs"` 的边，
   做成多层图（`docs/03` 有扩展点表）。
4. **视口裁剪**：为上千要素的规模做准备。
5. **3D 联动**：2D 选点 → 3D 高亮；3D 行走 → 2D 跟随。见 `docs/08`。

## 8. 不要动的地方

这些是经过验证的硬约束，改之前请先在群里讨论：

- **`data/campus/` 的坐标单位与朝向**（米 / x 东 / y 北）——3D 已经按这个对齐。
- **多边形绕向**（外环 CCW）——改了 3D 挤出的法线会反。
- **`graph.json` 的字段名**（`from`/`to`/`weight`/`adjacency`）——3D 也在消费。
- **零依赖原则**——引入 npm 包会破坏离线可用和 AI 可读性。
- **`.bat` 纯 ASCII**——见 `docs/00` 的常见问题。
