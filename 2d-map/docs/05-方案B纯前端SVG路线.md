> **57 项断言**全绿；项目体积 94.4 MB → 0.34 MB。
> 本文档保留当初的验证过程与依据；**迁移结果见第 4、5 节**，

## 1. 为什么方案B契合你们的新约束

你们的两条约束直接改变了技术选型的判据：

| 约束 | 对选型的影响 |
|------|--------------|
| 用 AI 工具做主要开发 | 源文件必须**纯文本、可 diff、可被 grep/读文件理解**；不能有 GUI 工程文件、二进制中间产物、需要点界面才能改的东西 |
| 虚拟构建的校园，没有真实影像 | **不需要地理配准、不需要瓦片、不需要 QGIS 描摹**；经纬度都可以不要 |

原方案（Leaflet + Esri 影像瓦片 + QGIS 数字化 + PyInstaller 打包 exe）在这两条约束下都成了负担：

- 832 片 JPEG 瓦片（9.9 MB）是二进制，AI 读不了、diff 不了、也无法编辑；
- QGIS 工程（`.qgz`）是压缩二进制，AI 完全无法读写；
- 两个 `.exe`（18.6 MB）是打包产物，AI 看不到里面的逻辑，改动要重新打包；
- Leaflet 虽是 JS，但它是**外部依赖**，AI 改不了它的行为，遇到问题只能绕。

方案B 把地图变回"**一堆可以用文本编辑器改的代码**"。

### 方案B 的"可读性"不只是口号

每个地图要素都是**真实 DOM 节点，且带语义属性**：

```html
<polygon class="building" data-id="bld0" data-name="图书馆"
         data-type="教学" data-floors="4" points="..."/>
<polyline class="footway" data-name="中央步道" data-from="cross_main" data-to="A_s" .../>
<g class="route" data-from="south_gate" data-to="east_jct"
   data-distance-m="468.2" data-nodes="south_gate>cross_main>lab_s>gym_s>east_jct">…</g>
```

也就是说：**路径算得对不对，不用看像素——读 DOM 属性就知道**。
AI 可以直接 `grep data-name` 找到某个建筑、改 CSS 调整样式、加一个事件监听，
整个链路都在它能读写的文本里。

## 3. 三个关键结论（均已自动化验证）

### 结论一：算法层可以脱离浏览器验证

`geo.js` 写成浏览器/Node 双用，于是"投影对不对、最短路对不对"用一条命令就能断言，
不需要开浏览器、截图、或人眼判断：

```bash
node web/verify.js          # 57 项断言，退出码即结论
```

实测结果（全部通过）：

```
3) 局部投影
  ✓ 投影画布 691 m × 469 m
  ✓ 所有要素坐标都落在投影画布内
  ✓ 每度换算 kx=88516.1 m/°经, ky=110985.6 m/°纬
  ✓ 投影在校园尺度下保距（最大相对偏差 0.239%）
4) Dijkstra 正确性
  ✓ 全部 136 个节点对均连通
  ✓ 距离对称   ✓ 满足三角不等式   ✓ 自身到自身为 0
5) 路径几何拼接
  ✓ 全部 136 条路径几何连续且首尾对位
  ✓ 路径几何长度与权重距离一致（实测最差 0.00%）
6) 性能
  ✓ 5000 次查询耗时 7 ms（0.001 ms/次）
7) 前端契约
  ✓ 18 个 $('#id') 选择器都在 index.html 中存在
  ✓ 9 个动态 class 都有 CSS 规则
  ✓ index.html 不引用任何外部资源（零依赖 / 可离线）
```

> 顺带查出一个真 bug：原来按"每度 110540 米"这个平均常数做换算，
> 在 37.4°N 会把南北向距离**整体低估约 0.4%**。改用 WGS84 曲率半径
> （M=6359006, N=6386036）后，失真降到 0.239%。

### 结论二：虚拟校园可以彻底不要经纬度

这是对你们最重要的一条。原型里 `makePlanarProjection()` 与地理投影返回**同一形状**，
下游（Dijkstra、路径拼接、SVG 渲染）一行都不用改。验证方式不是"看代码像对的"，
而是**同一份数据分别走两种坐标系，要求结果完全一致**：

```
3b) 平面坐标模式（虚拟校园可彻底不要经纬度）
  ✓ 平面投影画布 691 × 469（无任何地理换算）
  ✓ 两种模式落到同一 SVG 坐标（最大偏差 2.8e-14 单位）
  ✓ 平面模式下 136 对路径距离与地理模式完全一致（最大差 0.0e+0 m）
```

**含义**：虚拟校园的自绘数据可以直接写平面坐标（单位米，如 `[120, 45]`），
不需要投影、不需要控制点、不需要 `affine_fit.py`、不需要 QGIS。
`docs/02-坐标系与仿射变换.md` 那套流程可以整体退休。

代价：失去与真实地理的对应关系（无法和 3D 平台按经纬度对齐）。
纯虚拟校园无所谓；若以后仍想保留地理锚点，用当前的经纬度模式即可，**两条路都已验证可用**。

### 结论三：方案B 与现方案的迁移成本很低

数据层（路网图 + 矢量数据）**结构完全复用**，渲染层直接消费，实测与 Leaflet 版
给出一致的路径结果。要迁的只有"渲染 + 启动"这两层。
（实际迁移时额外把经纬度换成了平面米坐标，见第 4、5 节。）

## 6. 已知边界（诚实说明）

- **渲染层没有做无头浏览器自动化测试**。57 项断言覆盖的是逻辑层 +
  "HTML id ↔ app.js 选择器 ↔ CSS class"的静态契约；DOM 交互（拖拽平移、
  滚轮缩放、点节点选起终点）只做了代码级修正（例如刻意不用
  `setPointerCapture`，因为它会把 pointerup 重定向到 `<svg>`，
  导致 click 目标退化、节点点不中），**但没有自动化验证**。请手动打开确认。
- 原型只支持"点选节点"式选点，没有自由起终点吸附（可后续加）。
- 虚拟校园规模放大到上千节点时，当前是"一次性渲染全部要素"，
  可能需要视口裁剪（性能上限见验证第 6 项，算法侧 0.001 ms/次，瓶颈在渲染）。
