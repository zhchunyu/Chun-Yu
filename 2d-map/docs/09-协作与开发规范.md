# 09 · 协作与开发规范

> 三个人 + AI 工具一起改同一个仓库，靠的不是默契，是**明确的约定和自动检查**。
> 这份文档就是那套约定。新人第一次提交前请通读一遍。

## 1. 仓库与访问

- **私有仓库**，成员 3 人，通过 GitHub 邀请加入。
- 主分支：`main`。**`main` 必须永远是绿的**（`node web/verify.js` 全过）。
- 仓库里不该出现的东西已经由 `.gitignore` 挡住（见第 8 节）。

### 首次配置

```bash
git clone <仓库地址>
cd <仓库目录>

# 设成你自己的信息（很重要，会写进提交历史）
git config user.name  "你的名字"
git config user.email "你的邮箱"

# 验证环境
python scripts/start_server.py      # 起服务
node web/verify.js                  # 应该 57 项全过
```

> 💡 邮箱建议用 GitHub 提供的 `noreply` 地址
> （GitHub → Settings → Emails → Keep my email addresses private），避免把真实邮箱写进公开历史。
> 另：如果不希望别人看到自己的个人邮箱，也可以直接填 GitHub 用户名 + noreply。

## 2. 分支与提交流程

采用**短分支**策略：改动小、合并快。

```bash
git switch main && git pull            # 1. 更新
git switch -c feat/building-heights    # 2. 开短分支
#   ...改代码...
node web/verify.js                     # 3. 本地自检（必做）
git add -A && git commit -m "..."      # 4. 提交
git push -u origin feat/building-heights
# 5. 在 GitHub 开 PR -> 至少 1 人 review -> 合并到 main
```

### 分支命名

| 前缀 | 用途 | 例 |
|------|------|-----|
| `feat/` | 新功能 | `feat/floor-navigation` |
| `fix/` | 修 bug | `fix/polygon-winding` |
| `data/` | 只改数据 | `data/add-library-floors` |
| `docs/` | 只改文档 | `docs/3d-integration` |
| `chore/` | 杂项 | `chore/bump-verify` |

### 提交信息

格式：`<前缀>: <一句话说明>`

```
feat: 节点支持 floor 字段，用于多层室内导航
fix: 修正操场被 3D 挤出的问题（补 kind=ground）
data: 图书馆层数改为实际 6 层
docs: 补充 Babylon.js 的坐标映射示例
```

规则：

- 一句话说清**做了什么**，不要写"update"、"修改"这种无信息量的。
- 一次提交只做一件事。数据改动和代码改动**不要混在一个提交里**
  （review 时很难看出是哪边引入的问题）。
- 破坏性变更（改坐标系/字段名/绕向约定）必须在正文里写清楚，
  **并且同步通知 3D 同学**（见 `docs/08` 第 13 节）。

## 3. 硬性门禁：改完必须跑验证

```bash
node web/verify.js      # 或双击 自检.bat
```

- **退出码 0 = 通过**，非 0 = 有问题。提交前必须是 0。
- **失败时不要改断言，去改代码/数据。** 断言是契约，不是障碍。
  确实断言本身写错了（比如基准值过时），要在 PR 里说明为什么改。
- CI 接上后这条会变成 PR 的必过检查。

为什么这么强调：这个项目的核心设计就是**正确性可自动验证**——
`web/geo.js` 是纯逻辑层，能在命令行直接断言。
如果你绕过它靠肉眼检查，等于放弃了项目最大的优势。

## 4. 代码约定

### 分层：算的放 `geo.js`，碰 DOM 的放 `app.js`

| 文件 | 允许做什么 | 不允许做什么 |
|------|-----------|-------------|
| `web/geo.js` | 纯计算：坐标、几何、图算法 | ❌ 碰 DOM、`window`、`fetch` |
| `web/app.js` | DOM 操作、事件、渲染 | ❌ 塞入可复用的算法逻辑 |

**判断标准**：这段逻辑能不能用 `node` 断言？能 → 放 `geo.js` 并补断言；不能 → 放 `app.js`。

### 零依赖

**不要引入 npm / pip 包。** 需要新能力时优先手写几十行。

原因：① 保证离线可用；② 外部库是 AI 改不动的黑盒；③ 这个项目的规模不需要。
如果确实认为必须引入，**先在群里讨论**。

### 地图要素要带语义属性

新增任何渲染出来的要素，都要带上 `data-*`：

```js
el('polyline', {
  points: ...,
  class: 'footway',
  'data-id': 'fw' + i,
  'data-name': f.properties.name,   // 人/AI 都能按名字检索
  'data-type': 'footway',
}, layers.footways);
```

这样 AI 和协作者都能 `grep data-name="图书馆"` 直接定位，不用反推渲染顺序。
算出来的结果（如路线距离）也要写进属性：

```html
<g class="route" data-distance-m="468.2" data-nodes="south_gate>cross_main>...">
```

### `.bat` 文件必须纯 ASCII

cmd.exe 按字节偏移解析批处理文件，UTF-8 中文会把**后面的命令行**吃掉。
这个坑真踩过：`node web\verify.js` 被解析成了 `e.js`。

保持纯 ASCII；要写中文说明就放注释里的 Markdown 文档。

### Python 脚本只用标准库

`scripts/*.py` 目前全部只依赖标准库，请保持。

## 5. 数据改动的标准流程

数据是三个人最容易互相踩的地方（尤其 3D 同学会改建筑高度）。请严格按流程：

```
① 改 data/campus/*.json          （手写或脚本生成）
② 若是节点/道路改动 → 重建图      python scripts/build_graph.py
③ 跑验证                          node web/verify.js
④ 提交（单独一个 data: 提交）
```

### 改动影响速查

| 改了 | 需要重建图？ | 需要通知 3D？ |
|------|-------------|---------------|
| 建筑轮廓 / 层数 / 高度 / kind | ❌ | ✅（他们要用高度） |
| 道路中线 | ✅ | ✅ |
| 节点位置 / 新增节点 | ✅ | ✅ |
| 只改 2D 样式（`style.css`） | ❌ | ❌ |
| 改了坐标系约定 / 绕向 / 字段名 | ✅ | ✅✅ **必须先讨论** |

## 6. 跨文件改动 Checklist

最容易出错的是"改了一处忘了另一处"。照着清单走。

### 新增一栋建筑

- [ ] `data/campus/buildings.json` 加一个 Polygon
- [ ] 外环**逆时针**、坐标**首尾闭合**
- [ ] 有 `name` / `type` / `floors`（面状设施加 `kind: "ground"`）
- [ ] `node web/verify.js` 通过（建筑不需重建图）

### 新增一条路

- [ ] `data/campus/nodes.json` 加两端节点（若已存在则跳过）
- [ ] `roads.json` 或 `footways.json` 加 LineString，`from`/`to` 指向节点 id
- [ ] 线的**首坐标 = from 节点坐标，尾坐标 = to 节点坐标**
- [ ] 重建图：`python scripts/build_graph.py --out data/graph.json`
- [ ] `node web/verify.js` 通过

### 移动一个节点

- [ ] 改 `nodes.json` 的坐标
- [ ] **同步改所有引用该节点的边的端点坐标**（否则验证会报"几何与节点不对位"）
- [ ] 重建图 + 跑验证

### 改坐标约定 / 字段名 / 绕向

- [ ] **先在群里讨论**——这会同时影响 2D、3D 和数据管线
- [ ] 提升 `data/*.json` 里的 `format` 版本号
- [ ] 更新 `docs/06`、`docs/08`
- [ ] 更新 `web/verify.js` 的断言
- [ ] 通知 3D 同学同步他们的复制件

## 7. AI 协作约定

这个项目是为 AI 辅助开发设计的，用 AI 改代码时请遵守：

1. **改完必须跑 `node web/verify.js`**，非 0 就继续修，**不要让它去改断言**。
2. **告诉 AI 去读文档**：`docs/06`（数据规范）、`docs/08`（3D 契约）是契约来源，
   不要让 AI 猜字段含义。
3. **不要让 AI 手改 `data/graph.json`**——它是派生产物。
4. **不要让 AI 引入依赖**。如果它建议装包，先质疑。
5. **AI 的输出要过验证再提交**。断言全绿是最低门槛，不是质量保证；
   涉及 3D 视觉效果的改动仍需人来确认。
6. **把断言当护栏用**：如果你发现 AI 反复犯同一类错，就补一条断言。

## 8. `.gitignore` 说明

仓库里**不应该**出现：

| 模式 | 原因 |
|------|------|
| `__pycache__/`、`*.pyc` | Python 字节码 |
| `.venv/`、`venv/`、`env/` | 本项目零依赖，不需要虚拟环境 |
| `node_modules/` | 零依赖，不需要 |
| `.DS_Store`、`Thumbs.db`、`desktop.ini` | 系统垃圾文件 |
| `*.exe`、`*.dll` | 二进制黑盒（本项目的明确取舍） |
| `web/lib/tiles/` | 影像瓦片（虚拟校园不需要） |
| `*.qgz`、`*.shp`、`*.dbf`、`*.tif` | GIS 二进制格式（已退役的路线） |
| `.vscode/`、`.idea/` | 编辑器配置（个人偏好） |
| `*.log` | 日志 |

**判断标准**：如果一个文件 AI 读不了、或者可以用一条命令重新生成，它就不该进仓库。

### 一个例外：`data/graph.json` 是**故意提交**的

它虽然是 `build_graph.py` 的派生产物，但**要进仓库**，原因：

1. 3D 同学可以直接消费它，不必装 Python、不必跑构建脚本；
2. Web 端 / 演示 / 评审时开箱即用；
3. 它有**断言保护**——`verify.js` 第 3 节会检查它与 `data/campus/*.json` 是否同步，
   所以"派生物和源数据漂移"这个经典问题在这里不会发生。

因此：**它可以提交，但永远不要手工编辑它**。要改就改 `data/campus/`，然后重新生成。

## 9. Review 与冲突

### PR 评审重点

- [ ] `node web/verify.js` 是否全绿？（CI 会查，但请自己也看一眼）
- [ ] 数据改动是否遵守了对应 Checklist？
- [ ] 是否引入了新依赖？（应该没有）
- [ ] 破坏性变更是否更新了 `format` 版本号和文档？
- [ ] `data/` 和 `code/` 的改动是否分开提交？

### 冲突高发区

| 文件 | 谁常改 | 怎么避免 |
|------|--------|----------|
| `data/campus/buildings.json` | 2D 和 3D 都会改（高度） | 改之前说一声；一个 feature 一个区块，冲突好解 |
| `data/graph.json` | **派生产物，最容易冲突** | 它由脚本生成——冲突时不要手工合并，直接重建图 |
| `web/verify.js` | 加断言的人多 | 追加新 section，少改已有断言 |
| `README.md` | 都会改 | 只改自己负责的章节 |

> **`data/graph.json` 的冲突处理**：不要手工解决冲突。
> 直接 `python scripts/build_graph.py --out data/graph.json` 重新生成，然后提交。

## 11. 把项目放进共享仓库

本项目通常是**整个三维数字校园仓库里的一个模块**（放在如 `2d-map/` 的子目录），
而不是一个独立仓库。分三种情况。

> **好消息：放进子目录不需要改任何代码。** 所有内部路径都是相对的——
> `web/app.js` 用 `../data/…`、`web/verify.js` 用 `__dirname/..`、
> `scripts/start_server.py` 按自身位置定位项目根。
> 已实测：嵌套后 57 项断言全绿，`/web/` 与 `/data/` 均正常返回。

### 情况 A：仓库已存在，你是新加入的协作者（最常见）

用网页上传即可，**不需要 push 权限，也不会误覆盖别人的文件**：

1. 先准备一份**不含 `.git`** 的干净副本。
   ⚠️ Windows 资源管理器默认隐藏点文件，手动复制极易漏掉 `.gitignore` / `.gitattributes`，
   请用 robocopy：

   ```powershell
   robocopy <项目目录> <目标目录>\2d-map /E /XD .git
   ```

2. 打开仓库页面 → **Add file → Upload files**
3. **拖拽整个 `2d-map` 文件夹**进去。
   ⚠️ 不要点 "choose your files" 去浏览选择——文件选择器会**跳过** `.gitignore` 这类点文件。
   （单次拖拽上限 100 个文件，本项目 54 个，没问题。）
4. 提交选项：**选 "Create a new branch for this commit and start a pull request"**
   - 分支名建议：`feat/2d-map-initial`
   - **Commit summary 别用默认的 "Add files via upload"**，写清楚，例如：
     `feat: 加入 2D 校园导航地图模块（方案B 纯前端 SVG）`
5. 上传后**核对两个点文件**在不在：`2d-map/.gitignore`、`2d-map/.gitattributes`。
   漏了就用 Add file → Create new file 补上（内容见仓库里的同名文件）。
6. 开 PR，请仓库 owner review 后合并。

> ⚠️ **不要选 "Commit directly to the main branch"**，两个原因：
> ① 多数共享仓库的 `main` 开了分支保护，直接提交会失败；
> ② **网页上传对同名文件是直接覆盖，没有 diff、没有警告**——
>    万一撞上队友的文件就找不回来了。

### 情况 B：你有 push 权限，想用 git（更推荐，保留提交历史）

```bash
git clone https://github.com/<owner>/<repo>.git campus-shared
cd campus-shared
robocopy <项目目录> .\2d-map /E /XD .git
git add 2d-map
git commit -m "feat: 加入 2D 校园导航地图模块（方案B 纯前端 SVG）"
git push -u origin HEAD
```

**之后的日常开发就在 `<repo>/2d-map/` 里进行**——本地与远程结构一致，
`git pull` / `git push` 才是对的。不要在别处再留一份副本，否则必然分叉。

### 情况 C：你是仓库负责人，要新建一个仓库

1. GitHub → New repository → 选 **Private** → **不要**勾 "Add a README" → Create
2. 本地执行：

   ```bash
   git remote add origin https://github.com/<你的用户名>/<仓库名>.git
   git branch -M main
   git push -u origin main
   ```

3. 加协作者：Settings → Collaborators → 邀请另外两人。

> **推送认证**：GitHub 已不支持密码，需要 **Personal Access Token**
> （Settings → Developer settings → Personal access tokens → Tokens (classic)，
> 勾 `repo` 权限）。推送时用户名填 GitHub 用户名，**密码填这个 token**。
> 也可以装 GitHub CLI：`gh auth login` 之后
> `gh repo create <名字> --private --source=. --remote=origin --push`。
>
> ⚠️ **不要把 token 贴到聊天/issue/文档里**——它是你账号的完整写权限。

## 12. 有问题怎么办

- **看不懂架构** → `docs/07-技术路线与架构.md`
- **不知道怎么改数据** → `docs/06-虚拟校园数据规范.md`
- **要接 3D** → `docs/08-与3D地图对接.md`
- **验证报红但看不懂** → 断言信息里带了具体文件和数据，先看它指出的那条；
  实在不行把完整输出发到群里
- **想改约定** → 先在群里讨论，别自己改（会影响另外两个人）
