# 02 · 坐标系建立与仿射变换（方案 3.1 的落地）

核心问题：**屏幕像素坐标 ↔ 真实地理坐标** 如何对应。本项目采用三层坐标体系，
全流程统一到 **WGS84 经纬度（EPSG:4326）**，这也是 2D/3D 联动的共同基准。

## 1. 三层坐标体系

```
底层  WGS84 经纬度 (lon, lat)      ← 全局统一基准，GeoJSON/3D 场景都用它
中间  平面米制坐标 (x, y)          ← UTM / Web Mercator，算距离、算面积用
顶层  底图像素坐标 (px, py)        ← 只在描摹未配准的平面图时临时存在
```

- `geojson_to_graph.py` 内部用 **Haversine 公式**直接在经纬度上算边长（米），
  所以中间层大多不必显式落盘；需要精确平面计算时用 pyproj：

```python
from pyproj import Transformer
# WGS84 -> UTM 50N（北京一带）
t = Transformer.from_crs("EPSG:4326", "EPSG:32650", always_xy=True)
x, y = t.transform(116.3100, 39.9700)   # 米
# WGS84 -> Web Mercator（与 Leaflet/主流 3D 引擎一致）
t2 = Transformer.from_crs("EPSG:4326", "EPSG:3857", always_xy=True)
```

## 2. 控制点采集（至少 4 个，推荐 6~10 个）

选**分布均匀、能精确定位**的地物：建筑角点、路口中心、操场四角。
每个点记录一对坐标：

| 记录方式 | 像素坐标 px,py | 经纬度 lon,lat |
|---------|----------------|----------------|
| 底图上 | 用画图软件/QGIS 在图片上读出 | — |
| 实地 | — | 手机 GPS（地图 App 长按取点）或无人机 POS |

写进 CSV（格式模板见 `data/control_points.example.csv`）：

```
pixel_x,pixel_y,lon,lat
120,340,116.31021,39.97153
...
```

> 经纬度小数位保留 5 位以上（约 1 米精度）；避免只取一条线上的点（会退化）。

## 3. 标定与转换

```bash
# ① 标定：输出六个仿射参数 + 每点残差 + RMSE
python scripts/affine_fit.py data/control_points.csv

# ② 应用：把像素坐标的 GeoJSON 批量转为经纬度
python scripts/affine_fit.py data/control_points.csv --apply data/raw/sketch.geojson data/raw/campus_wgs84.geojson

# ③ (可选) 保存参数，供 3D 侧/其他脚本复用
python scripts/affine_fit.py data/control_points.csv --save data/affine.json
```

模型：`lon = a0 + a1*px + a2*py`，`lat = b0 + b1*px + b2*py`（最小二乘六参数）。

**精度判读**：
- RMSE ≤ 3 m：可用；
- 3~10 m：增加控制点数量，尤其是图幅四角与中部；
- 反复偏大：底图本身有透视/纸张变形，先拉直再扫描，或分块标定。

## 4. 与 3D 场景对接（方案 3.2 → 采用方案一：共享经纬度）

1. **约定基准**：项目初期与建模同学确认 3D 场景以 WGS84 经纬度为世界坐标
   （或以校园中心为原点的米制坐标，但必须给出中心点经纬度 + 一条轴的方位角）。
2. **交换锚点**：双方互给 2~3 个同名锚点的坐标（校门中点、图书馆角点…），
   2D 侧验证：`affine_fit` 后这些点落在路网正确位置；3D 侧验证：模型摆位一致。
3. **运行时联动**：二三维联动时同步"地图中心经纬度 + 缩放级别 ↔ 相机高度"即可。
   Web Mercator（EPSG:3857）是 Leaflet 与多数 WebGL 场景的公共语言，转换用上面的 pyproj 两行。
